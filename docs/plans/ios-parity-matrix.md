> The single coordination checklist for the native iOS client build.
> Generated at Phase 3 kickoff from the live Android screen inventory
> (`android/feature-*` + `android/app`) and the Phase 3 wave table in

> Created 2026-09-22.

## What this file is

Per the plan's **Coordination rules** (§ "Coordination rules", rule 1), this
matrix is the *single* checklist that tracks Android → iOS parity. It is the
shared source of truth for the fan-out in Phase 3 and the audit loop in
Phase 4:

- **Every Phase 3 agent** owns one wave/row cluster and **checks off its rows
  in the same PR** that delivers the SwiftUI views + platform services +
  tests. A PR that ships a screen but leaves its Status unchanged is
  incomplete.
- **Every Phase 4 parity-auditor agent** flips a row to `Verified` only after
  diffing the Android screen source (source of truth) against the shipped iOS
  view, or files a gap and leaves it below `Parity`.
- The **contract guard** and **reviewer** roles do not edit this file except
  to correct drift they observe.

Agents never share a branch; interface changes to `shared/` are escalated
separately (rule 2). This file, however, is edited by many PRs — keep edits
row-scoped to avoid merge churn (see the footer).

### Status column semantics

| Status | Meaning |
|---|---|
| **Not started** | No iOS view file exists yet. |
| **Scaffold** | Route/stub view exists in the Phase 2A navigation skeleton (renders a placeholder, observes no data). |
| **In progress** | iOS view under active construction; not yet behavior-complete. |
| **Parity** | iOS view is behavior-complete vs. the Android screen; author asserts parity; tests green. |
| **Verified** | A Phase 4 parity auditor independently confirmed parity against Android source (two consecutive dry audit rounds close the screen). |

Initial state (this commit): the top-level destinations the Phase 2A scaffold
agent stubs — **Today, Workouts hub, Nutrition today, Medications list, Blood
overview, Body composition, Goals list, Settings, More** — start at
`Scaffold`. Everything else starts at `Not started`.

### Wave legend (from the plan's Phase 3 table)

`A1` Dashboard/Today · `A2` Settings · `B` Medications · `C` Nutrition ·
`D` Workouts (i hub / ii live session / iii designer+progression+gyms) ·
`E1` Blood · `E2` Body composition · `E3` Goals · `F` iPad/accessibility polish
(applies across all rows).

iOS view target root: `ios/HealthFitness/Features/…` (paths below are relative
to that root). Shared VM names are the KMP `shared/presentation` ViewModels
extracted in Phase 1D (same class name as the Android `*ViewModel`).

## How to update this file

1. **You own rows, not the file.** When your Phase 3/4 PR delivers a screen or
   mechanism, edit only that row's **Status** cell (and, if you renamed the iOS
   file, its `iOS view` cell). Do not reflow tables or touch other rows —
   this keeps many parallel PRs from conflicting.
2. **Status flow:** `Not started` → `Scaffold` (2A only) → `In progress` →
   `Parity` (you, when behavior-complete + tests green) → `Verified` (Phase 4
   auditor only). Never mark your own row `Verified`.
3. **Update in the same PR as the code.** A screen PR that leaves its row
   unchanged is not done (plan § Coordination rules, rule 1).
4. **New Android screen appears?** Add a row in the correct feature-area table,
   assign a wave, and set Status = `Not started`. Note it to the wave lead so
   it enters the audit set.
5. **Found a parity gap in audit?** Leave the row below `Parity`, and file the
   specific missing behavior as a checklist sub-note or a linked issue —
   auditors are adversarial and close a screen only after two consecutive dry
   rounds (plan § Phase 4).
6. **Keep the source-of-truth link live:** Android `*Screen.kt` paths are
   relative to `android/feature-*/src/main/java/com/gte619n/healthfitness/…`
   (or `android/app/…` for the `app`-module rows). iOS paths are relative to
   `ios/HealthFitness/Features/`.
