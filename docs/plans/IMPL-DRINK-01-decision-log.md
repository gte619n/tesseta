# IMPL-DRINK-01 — Implementation Decision Log

Running log of decisions made **during implementation** (distinct from the interview decisions D1–D22 in the spec). Each entry: what was decided, why, and any follow-up to review.

Format: `IL-<n>` (Implementation Log). Newest at the bottom.

- **IL-1** — *Decision log location & granularity.* Keeping a single flat log at `docs/plans/IMPL-DRINK-01-decision-log.md` rather than per-phase logs (matches IMPL-16/IMPL-18 precedent). Every non-obvious implementation choice — naming, where a field lives, a deviation from the spec, a reuse vs new-code call — gets an entry. **Review:** none.

- **IL-2** — *`AlcoholInfo` lives on `CatalogFood` only, NOT on `FoodEntry`.* The spec (§3.5, task 0.2) contemplated a frozen `AlcoholInfo` snapshot on the entry so the day view could show per-entry standard drinks. On implementation I found (a) alcohol **calories** already ride the entry's frozen `macros.caloriesKcal` (so F14 "daily total includes alcohol kcal" is satisfied without it), (b) the live session tally (std drinks) is a client-side concern computed from the locally-cached catalog's `AlcoholInfo` (D14/§4.3), and (c) recents join back to the cached catalog by `foodId` for any std-drink display. Adding a positional field to the 20-field `FoodEntry` record would ripple through **18 constructor sites** + Firestore ser/de + `EntryResponse` for no functional gain in MVP. **Decision:** entries stay unchanged; only `CatalogFood` gains `alcohol` + `archivedAt`. **Review:** if a future requirement needs per-entry std-drink display in the *synced* day view (e.g. web history), revisit — the catalog join covers today's needs.

- **IL-3** — *Drink calorie model bypasses `Macros.withDerivedCalories()`.* `FoodCatalogService.create()` normally calls `withDerivedCalories()` (calories = 4·protein+4·carbs+9·fat), which would **erase alcohol calories**. Drinks instead compute serving calories explicitly as `4·protein + 4·carbs + 9·fat + 7·alcoholGrams` and store macros **without** re-derivation. Implemented as a dedicated `FoodCatalogService.createDrink(...)` path. **Review:** none — this is required for correctness.

- **IL-4** — *Drink stored as per-100(ml≈g) macros to reuse the existing scaling model.* A drink has one serving (the glass, `servingVolumeMl`). To make the long-press ×0.5/×1/×2 multiplier (D22) reuse the existing `quantity`-based entry scaling, the drink's `servingSizes=[{label, grams=servingVolumeMl}]` and `macrosPer100g = servingMacros × (100/servingVolumeMl)`. Logging with `quantity=q` then yields `servingMacros × q` (alcohol calories included) — no new scaling code. `AlcoholInfo` describes the **default serving**; client multiplies std-drinks by `q`. **Review:** density approximation (1 ml ≈ 1 g) is irrelevant here since grams is only a scaling denominator, not a displayed weight.

- **IL-5** — *Drink analyzer returns component macros + ABV + volume; backend derives alcohol + calories.* Per D10 (deterministic/auditable), the Gemini `DrinkExtractor` returns `{name, abvPercent, servingVolumeMl, proteinGrams, carbsGrams, fatGrams, sugarGrams}` (the mixer/sugar contribution, per serving, EXCLUDING alcohol calories). The backend computes `alcoholGrams`, `standardDrinks`, and total `caloriesKcal`. Keeps the AI out of the arithmetic. **Review:** none.

- **IL-6** — *Drink logging reuses the standard `POST /{date}/entries` add-entry path.* No new logging endpoint or op type (spec §3.2). Android logs a drink as an ordinary entry with `meal=DRINKS`, `foodId`=drink id, frozen `macros`, `source=CATALOG`, `date`=session-start day. Fully reuses the existing offline op rail + idempotency. **Review:** none.

- **IL-9** — *Web is setup-only, built with the existing server-component + server-action pattern.* `/me/drinks` page + `web/lib/drinks-api.ts` + `web/components/drinks/*`. The web form re-derives per-serving mixer macros from `macrosPer100g × servingGrams/100` because `FoodResponse` only echoes per-100g macros (not the per-serving mixer split); an edit round-trip can drift by tiny float rounding. Day view: `DRINKS` added to the `Meal` union + labels/icons but **kept out of** the always-present `MEALS` array, so the Drinks section renders only when it has entries (D8). Verified via `pnpm build/lint/test`. **Review:** the per-serving re-derivation drift is cosmetic; if it ever matters, have the backend echo the stored per-serving mixer macros on `FoodResponse`.

- **IL-10** — *Android stored drinks in the existing `catalog_cache` opaque JSON instead of adding Room columns — NO migration.* The spec (task 2.2) anticipated a v7→v8 additive migration for alcohol columns. The Android subagent instead serialized `AlcoholInfo` inside the cache row's existing opaque payload JSON (keyed `type="drink"`), so **no schema bump** and the in-flight `nutritionOps` queue is untouched (avoids the #219-style wipe risk entirely). Lighter and safer than planned. **Review:** confirm the cache payload is the canonical `FoodResponse` JSON so `alcohol` survives round-trips; if drink search ever needs SQL-level alcohol filters, revisit with real columns.

- **IL-11** — *Android uses a wire-string `"DRINKS"`, not a new `Meal` enum value.* Drinks log only from the card (never the meal pickers), so the subagent added a `DRINKS_WIRE`/`DRINKS_MEAL` constant rather than extending the `Meal` enum — and `assembleDay` explicitly builds the DRINKS group + counts it in totals so entries are never dropped (the past enum-drop bug class). Verified by code review + it compiles (no exhaustiveness break). **Review:** if any future UI needs to *pick* DRINKS as a meal, promote it to the enum then.

- **IL-8** — *Fan-out collection for drink writes is `foodCatalog`.* Drink mutations call `syncNotifier.changed(userId, originDeviceId, "foodCatalog")`. Since `foodCatalog` is not a synced *mirror* (IL/spec §3.2), this is only a wake signal telling other devices to re-warm their local drink cache; it costs nothing if no client acts on it, and keeps parity with how other catalog writes notify. **Review:** confirm Android treats a `foodCatalog` change notification (if surfaced) as a cue to re-warm, or simply relies on foreground/enable warms — either is fine.
