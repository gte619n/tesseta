### OBS-001 — No alerting, no uptime checks, no error reporting: production has zero push-based signals
- **Severity:** critical | **Confidence:** [Certain]
- **Evidence:** Live REST reads above: `alertPolicies`, `uptimeCheckConfigs`, `notificationChannels`, log-based `metrics`, and `dashboards` all return empty `{}`; Error Reporting returns `SERVICE_DISABLED`. Repo-side corroboration: the entire Terraform estate is 251 LOC and manages only remote state (`infra/terraform/backend.tf`), provider pinning (`versions.tf`), CI secret IAM (`ci_iam.tf`), an opt-in staging Firestore DB (`staging.tf`, `enable_staging` default `false` in `variables.tf`), and one Firestore TTL field (`firestore_ttl.tf:33` `resource "google_firestore_field" "idempotency_keys_ttl"`). No `google_monitoring_*` resource exists anywhere in the repo.
- **Impact:** Every failure class is discovered by the operator noticing app misbehavior. This is the root enabler of all four cited incidents. Minimal signals that would have caught them:
  - *Weeks of silent deploy failures* → an alert on Cloud Build `status=FAILURE` (log-based metric or Cloud Build Pub/Sub notifier).
  - *FCM dead in prod (cert mismatch)* → uptime-style daily check that `fcmTokens` registry is non-empty / a log-based metric on the FCM warn lines (see OBS-006).
  - *Cloud Tasks 401 loop* → log-based metric on `"Nutrition job rejected"` (`NutritionJobController.java:70`) with a >0 alert.
  - *Webhook-as-probe drops* → ratio alert on probe-accepted vs UPSERT log lines (see OBS-009).
  Also: the public `/actuator/health` endpoint exists (`backend/src/main/resources/application.yml:45-53` exposes `health,info`) but nothing probes it — a bad revision that passes the one-shot canary (`infra/scripts/canary-promote.sh`) and degrades later is invisible.
- **Effort:** 1–2 days (enable Error Reporting API — one click, free; 1 email notification channel; ~6 log-based metrics + alert policies; 2 uptime checks on `api.tesseta.com/actuator/health` and `app.tesseta.com`; commit as `infra/terraform/monitoring.tf`).
- **Autonomy:** High — Terraform + gcloud, no app code.
- **Null-option cost:** Next silent outage runs for days-to-weeks again; for a health app with medication reminders, a silently-dead backend has user-safety implications, not just UX.
- **Prompt:** "In infra/terraform, add monitoring.tf for project health-fitness-160: (1) a google_monitoring_notification_channel (email, operator address from a variable); (2) uptime checks + associated alert policies for https://api.tesseta.com/actuator/health and https://app.tesseta.com; (3) log-based metrics + >0 alert policies for: Cloud Build status=FAILURE, textPayload:'Nutrition job rejected', textPayload:'push dropped: no FCM tokens', Cloud Run Job execution failures (resource.type=cloud_run_job severity>=ERROR); (4) enable clouderrorreporting.googleapis.com. Keep everything in the existing variables.tf style; do not manage Cloud Run services."

### OBS-002 — No crash/error reporting from any client (Android phone, Wear, web)
- **Severity:** critical | **Confidence:** [Certain] (absence verified in dependency manifests)
- **Evidence:** `android/gradle/libs.versions.toml:144-145` declares only `firebase-bom` + `firebase-messaging` — no Crashlytics artifact anywhere (`grep -riE "crashlytics|sentry|bugsnag"` over `android/` build files: zero hits) even though the google-services plugin and `FirebaseApp` bootstrap are already wired (`android/app/build.gradle.kts:203-206`). `web/package.json`: no sentry/bugsnag/datadog/rollbar/analytics dependency (grep zero hits). Web error boundaries swallow errors locally: `web/app/global-error.tsx` and `web/app/error.tsx` both do only `useEffect(() => { console.error(error); }, [error])` — a browser console nobody sees. Same pattern in `web/app/admin/error.tsx`, `web/app/me/error.tsx`.
- **Impact:** For a Play-distributed app, a crash loop on user devices (e.g. a bad sync payload crashing the FCM handler fleet-wide) produces **zero** operator signal — users cannot effectively report, and Play Console ANR/crash vitals are the only (slow, unconfigured) fallback. The FCM cert-mismatch incident is exactly this class: the *client-side* symptom (Firebase Installations 403 on every device, logged only to logcat in `android/app/src/main/java/com/gte619n/healthfitness/mobile/push/TokenRegistration.kt:73,103,115`) was invisible because nothing exfiltrates client errors. Web server-component errors land in Cloud Logging as unstructured text with no severity and are equally unwatched.
- **Effort:** 1 day Android/Wear (Crashlytics = 1 plugin + 1 dep per module; Firebase project already configured), 0.5–1 day web (Sentry free tier or GlitchTip; wire `global-error.tsx`/`error.tsx` + `instrumentation.ts` onRequestError).
- **Autonomy:** High.
- **Null-option cost:** A shipped crash regression is discovered only via Play vitals days later or a user giving up; on Wear (no easy user reporting path at all) it may never be discovered.
- **Prompt:** "Add Firebase Crashlytics to the tesseta Android app and wear modules (google-services + FirebaseApp already wired via android/app/google-services.json; BoM at libs.versions.toml `firebaseBom`). Add the crashlytics gradle plugin and dependency via the version catalog, record non-fatal exceptions in TokenRegistration.kt catch blocks and the sync engine. For web (Next.js 15, web/), add @sentry/nextjs (or GlitchTip-compatible DSN via env), report from app/error.tsx, app/global-error.tsx and instrumentation.ts onRequestError. No PHI in event payloads: scrub request bodies; send only digest/route/userId-hash."

### OBS-003 — Backend logs are unstructured text: no severity mapping, no trace/request correlation, split stack traces
- **Severity:** high | **Confidence:** [Certain] for config; [Likely] for the Cloud Logging severity consequence (standard Cloud Run behavior, not re-verified against live log entries)
- **Evidence:** `backend/src/main/resources/logback-spring.xml:3-10` — the whole config is the Spring default console appender: `<include resource=".../console-appender.xml"/> <root level="INFO"><appender-ref ref="CONSOLE"/></root>`. No JSON encoder, no `logging.structured.format` (Spring Boot 3.5 supports `ecs`/`gelf`/`logstash` natively), no `logstash-logback-encoder` in `backend/build.gradle.kts`. No MDC/trace usage anywhere: `grep -rn "MDC\|X-Cloud-Trace" backend/src/main/java` → zero hits. `backend/Dockerfile` sets no logging JVM opts.
- **Impact:** On Cloud Run, plain stdout lines are ingested with **default (unset) severity**, so `severity>=ERROR` filters and log-based severity metrics see nothing from the app — the 18 `log.error` and 108 `log.warn` call sites (survey: 174 SLF4J statements total in `backend/src/main/java`: 18 error / 108 warn / 34 info / 14 debug) are indistinguishable from info in Logs Explorer. Multi-line stack traces split into one LogEntry per line, and with no request/trace ID there is no way to correlate a stack trace to the request or user action that caused it. This is also a **prerequisite for OBS-001's severity-based alerts** and for Error Reporting grouping. Note: `log.debug` is enabled in prod (`logback-spring.xml:10` sets `com.gte619n.healthfitness` to DEBUG), which is what makes `FirebaseMessagingFcmSender.java:74-75`'s debug-gated FCM failure line actually emit — flipping this logger to INFO later would silently mute it.
- **Effort:** 0.5 day: add `logging.structured.format.console: ecs` (or logstash) to `application.yml` for the prod profile + a small MDC filter putting `X-Cloud-Trace-Context` into `logging.googleapis.com/trace`.
- **Autonomy:** High.
- **Null-option cost:** Every future incident investigation stays grep-through-interleaved-text; severity alerting from OBS-001 must fall back to brittle string matches.
- **Prompt:** "Backend is Spring Boot 3.5 on Cloud Run logging plain text via the default console appender (backend/src/main/resources/logback-spring.xml). Switch console output to structured JSON that Cloud Logging parses natively (Spring Boot's built-in structured logging or logstash-logback-encoder emitting `severity`, `message`, `logging.googleapis.com/trace`). Add a servlet filter that parses the X-Cloud-Trace-Context header into the trace MDC key formatted as projects/health-fitness-160/traces/{id}. Keep local dev human-readable (profile-gate the JSON format). Verify multi-line stack traces arrive as single LogEntries."

### OBS-004 — Deploy pipeline failures notify no one; job-image update steps swallow errors with `|| true`
- **Severity:** high | **Confidence:** [Certain]
- **Evidence:** Trigger definitions have no notification config: `infra/triggers/backend.yaml` is only name/serviceAccount/github/filename/includedFiles (same for `web.yaml`, `android.yaml`). ### OBS-008 — Cloud Tasks auth-reject path never marks the job record FAILED: the 401-incident failure mode is still a silent dead-end
- **Severity:** medium | **Confidence:** [Certain] (code path); [Likely] on queue-config side effect (queue not live-inspected)
- **Evidence:** `backend/src/main/java/com/gte619n/healthfitness/api/nutrition/NutritionJobController.java` `handle()`: the secret check happens **before** attempt accounting and returns 401 without touching the job record:
  ```java
  if (secret.isBlank() || !Objects.equals(secret, presented)) {
      log.warn("Nutrition job rejected — secret missing or mismatched");
      return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
  }
  ```
  The `lastAttempt → safeMarkFailed(job) + 200` terminal handling exists only in the `catch (RuntimeException e)` around `dispatcher.dispatch(job)`. So on a repeat of the secret-newline incident (or any future secret rotation mismatch), Cloud Tasks retries to `max-attempts` (queue created with `--max-attempts` in `infra/scripts/bootstrap-nutrition-jobs.sh:37,44`; Cloud Tasks has no dead-letter queue) and then **drops the task**, leaving the Room/Firestore job record in its pre-terminal state forever — the exact "capture stuck ANALYZING" symptom. The secret is now trimmed both sides (constructor comment, same file), which fixes the known trigger but not the failure mode. Day-read reconcile sweeps are the acknowledged backstop for *some* job types (cloudbuild.yaml comment: "the day-read reconcile sweep is the backstop either way").
- **Impact:** Any systematic 401/5xx-before-dispatch condition silently exhausts the queue again. Minimal signal that would have caught the original incident within minutes: an alert on the `"Nutrition job rejected"` log line (>0 in 5 min), or a Cloud Tasks queue-depth/oldest-task-age alert.
- **Effort:** 0.25 day: also honor `X-CloudTasks-TaskRetryCount` on the 401 path (mark failed on final attempt when the job body is parseable) — note the tension: marking failed requires trusting an *unauthenticated* body, so prefer the alert-only fix plus queue-depth monitoring; 0.25 day terraform alert.
- **Autonomy:** Medium (the 401-path design tradeoff needs operator sign-off; the alert is autonomous).
- **Null-option cost:** Repeat incident = every photo capture "Couldn't read photo" again, discovered by user experience rather than telemetry.
- **Prompt:** "NutritionJobController (backend .../api/nutrition/) 401-rejects Cloud Tasks deliveries on secret mismatch without ever marking the job record FAILED, so exhausted tasks strand records in ANALYZING (the Sept-2026 secret-newline incident shape). Do NOT mark records failed from unauthenticated requests. Instead: (a) include the retry count header in the existing WARN line so final-attempt rejects are identifiable; (b) add terraform log-based alert: >3 'Nutrition job rejected' in 5m; (c) add a Cloud Monitoring alert on cloudtasks.googleapis.com/queue/depth for queue nutrition-jobs > 10 for 15m."

- **Severity:** low | **Confidence:** [Certain] for cited lines; sweep method: grep of all `log.*` call sites in `backend/src/main/java` for token/body/payload/email/prompt/response interpolations
- **Evidence:** Policy: `docs/requirements/privacy-and-compliance.md:75-79` — "No PHI or tokens in logs. OkHttp logging is at `BASIC` ... the webhook logs the health user id but not payloads." Verified compliant: Android OkHttp at BASIC (`android/core-data/.../net/NetworkModule.kt:81` `HttpLoggingInterceptor().apply { level = HttpLoggingInterceptor.Level.BASIC }`); FCM senders log token *counts* not values (`FirebaseMessagingFcmSender.java:81` "FCM multicast send failed for {} token(s)"); webhook/integration logs carry userId + counts only (e.g. `WithingsSyncService.java:103` "Withings body import user={} stored={}" — userId logging is explicitly permitted by §6); auth package contains zero log statements; Gemini services log failure messages, never prompts/responses (`MealDescriptionExtractor.java:138` "Meal description extraction call failed: {}", e.getMessage()). **Caveats (would-emit findings per R4):** (1) `api/error/GlobalExceptionHandler.java:74` `log.warn("Bad request: {}", ex.getMessage())` and `:62` `log.warn("Not found: {}", ex.getMessage())` — `IllegalArgumentException`/`NoSuchElementException` messages originating in validation of user free-text (e.g. meal-adjust prompts, food names) can carry PHI verbatim into logs; the same messages are also returned to clients (`ErrorResponse`), so the log adds retention. (2) `api/goals/GoalChatController.java:204-205` forwards raw `e.getMessage()` into the SSE `error` event — an upstream Gemini exception message could embed prompt fragments (client-facing more than log-facing, but same hygiene). Both are message-dependent, not guaranteed leaks.
- **Impact:** Low-probability PHI-in-logs under the default 30-day `_Default` retention; would become higher-exposure if log export/longer retention is added per OBS-001/003.
- **Effort:** 0.25 day: whitelist known-safe validation messages or log exception class + a bounded/sanitized message.
- **Autonomy:** High.
- **Null-option cost:** Small standing §6 nonconformance; audit debt if the log pipeline is ever shared or retained longer.
- **Prompt:** "Privacy doc §6 (docs/requirements/privacy-and-compliance.md) forbids PHI in logs.
