# D15 — Developer Experience & Solo-Maintainer Leverage (DX)

Auditor: D15. Date: 2026-09-13. Mode: read-only (no builds executed; timings cited from repo docs).

## BLUF

This repo is in the top percentile for agent-context infrastructure: four accurate-in-spirit CLAUDE.md files with review-reject rules, a curated `docs/reference/` set, 21 ADRs, decision logs, a UAT harness with a Firestore emulator + dev-login seam, and an android inner loop that was deliberately engineered down to a measured 2s incremental build. The leverage gaps are all of one shape: **things the operator does by manual vigilance that should be push-based or CI-enforced.** The worst is deploy observability — merge-to-main silently deploys (or silently fails to deploy) production, the only failure signal is a check-run you must remember to look at, and the recovery playbook (headless-gcloud-is-dead, ADC + REST log reads) exists only in the operator's out-of-repo memory. Second tier: machine-checkable conventions exist (docs-lint script, pinned toolchains) but are not wired into CI, and there is no formatter/linter rail at all on android, so the solo reviewer is the style gate for every agent-authored diff. Third tier: the three highest-churn files are also 1,000–2,700 lines, which is exactly where agent context cost and merge conflicts concentrate. Clean-clone-to-productive: backend/web in <1h yes; the full `dev.sh` stack no (undocumented Tailscale + tailnet-HTTPS + ADC prerequisites, and three docs state the wrong backend port).

## Findings

### DX-001 — Silent prod-deploy failures: no alerting, and the recovery runbook lives outside the repo
- **Severity:** Critical · **Confidence:** [Certain] (absence verified) / [Likely] (recurrence cost)
- **Evidence:**
  - `/CLAUDE.md:61-64`: "**CI does not gate deploys.** … a green PR can still fail to deploy. The failure shows only in the `deploy-*-on-main` check-runs on the merge commit — **watch those after every merge**." Manual vigilance is the documented control.
  - `docs/reference/deployment.md:93-96` (promote-canary): "**On failure, traffic is left untouched** — a bad build never reaches users." Safe, but the failure mode is *silence*: prod pinned to a stale revision with no signal.
  - `/CLAUDE.md:70`: Trivy "runs only at deploy time, not in PR CI, so it can silently keep prod on a stale revision."
  - No alerting anywhere: `grep -rniE "notification|alert|pubsub" infra/terraform/*.tf infra/scripts/setup-cloud-build-triggers.sh` → zero hits; `infra/terraform/` contains only `backend.tf ci_iam.tf firestore_ttl.tf staging.tf variables.tf versions.tf`.
  - Runbook absence: `docs/reference/deployment.md:279-282` quick-ref offers only `gcloud builds list --ongoing`; a repo-wide grep for `x-goog-user-project|gcloud logging|logs read` finds nothing except an unrelated line in `docs/plans/IMPL-AND-20-offline-first-sync.md:628`. The known-working recipe (headless gcloud user-auth is broken; use ADC + `x-goog-user-project` REST for Cloud Build/Logging) exists only in operator memory, invisible to any agent debugging a deploy.
- **Impact:** The operator has been burned by multi-merge windows where nothing deployed. Every merge imposes a "go check the check-runs" tax; every deploy incident starts with re-deriving the log-access method — an agent asked to "figure out why prod is stale" has no in-repo path to the answer.
- **Effort:** 1 day (Cloud Build publishes to the `cloud-builds` Pub/Sub topic for free → one Terraform notification channel / Cloud Function → email-or-push on `FAILURE`/`TIMEOUT` of the three triggers; plus a `docs/reference/observability.md` capturing the ADC/REST log-read recipes and the "path-filtered checks go neutral and hide a red main" trap).
- **Autonomy:** High — an agent can write both the Terraform and the runbook; operator applies.
- **Null-option cost:** Recurrence of silent prod-staleness (already happened at least once); permanent per-merge attention tax; deploy knowledge remains keyed to one person's external memory.

### DX-002 — Merge-to-main is a prod deploy of a PHI system with no CI linkage and a deploy-time-only CVE gate — an unguarded agent danger zone
- **Severity:** High · **Confidence:** [Certain]
- **Evidence:**
  - `docs/reference/deployment.md:14-16`: "**merging to `main` is the production deploy.** … GitHub Actions gates what's *allowed* to merge; Cloud Build ships whatever lands on `main`." The two systems are explicitly independent (`deployment.md:6-12`).
  - `/CLAUDE.md:66-70`: the Trivy HIGH/CRITICAL gate runs *only* in the deploy pipeline, so a PR that is fully green can still be undeployable — discovered only post-merge (compounding DX-001).
  - Mitigations that do exist: canary `--no-traffic` + smoke test (`deployment.md:87-96`) — but the smoke test is `/actuator/health` / `/` only.
- **Impact:** For an operator who delegates to agents, "agent merges PR" ≡ "agent deploys production." There is no repo-level guardrail (required-check config is not in-repo; Cloud Build triggers don't consult commit status). The cheapest correctness fix is symmetry: run the same Trivy scan in `backend-ci.yml` on PRs so undeployable dependency states are caught pre-merge.
- **Effort:** 1 day (Trivy job in backend/web CI reusing the cloudbuild flags; document branch-protection expectations in `deployment.md`).
- **Autonomy:** High for the CI job; branch-protection settings need the operator.
- **Null-option cost:** Periodic post-merge fire drills on dependency drift (the "first backend-touching merge eats accumulated breakage" pattern); agents keep learning about deployability only after the deploy.

### DX-003 — Onboarding/agent docs are wrong about dev.sh: wrong port in three places, and three hard prerequisites are undocumented
- **Severity:** Medium · **Confidence:** [Certain]
- **Evidence:**
  - `infra/scripts/dev.sh:38`: `BACKEND_PORT=8090`. But `/CLAUDE.md:77` ("Starts backend on http://localhost:8080"), `/README.md:42` ("backend :8080 + web :3000"), and `docs/reference/deployment.md:41` ("Backend `:8080`, web `:3000`") all say 8080.
  - `infra/scripts/dev.sh:44`: `[[ -n "$TAILSCALE_BIN" ]] || { echo "Missing required tool: tailscale" >&2; exit 1; }` — dev.sh hard-fails without Tailscale, and needs tailnet HTTPS certificates enabled (`dev.sh:150-154`) and ADC (`dev.sh:17-18`: "Run `gcloud auth application-default login` once"). None of these appear in `/README.md` Quickstart or `/CLAUDE.md` Local Development.
- **Impact:** Clean-machine test fails: the documented one-command dev path exits on a machine without Tailscale, and an agent following CLAUDE.md will curl the wrong port. These files are the *agent onboarding contract*; a wrong port in the top-level CLAUDE.md is exactly the class of error that burns an agent-hour per occurrence.
- **Effort:** 0.25 days.
- **Autonomy:** High — pure doc fix + a `require`-style preflight message listing prerequisites.
- **Null-option cost:** Every new machine / fresh agent session re-pays the discovery cost; erodes trust in CLAUDE.md accuracy generally (its main asset).

### DX-004 — docs-lint exists but nothing runs it: conventions are machine-checkable and unenforced
- **Severity:** Medium · **Confidence:** [Certain]
- **Evidence:** `scripts/check-docs.mjs:1-5` ("docs-lint: guards against known documentation regressions … Run from the repo root") checks forbidden stale phrases + required docs across `docs/`, README, and all four CLAUDE.md files (`check-docs.mjs:45-52`). `grep -rn "check-docs" .github/workflows/` → no hits; the five workflows (`android-ci.yml`, `backend-ci.yml`, `web-ci.yml`, `codeql.yml`, `terraform-ci.yml`) have no docs-path trigger at all.
- **Impact:** The repo already invented the right mechanism for keeping agent-context docs truthful, then left it manual. DX-003's port drift is precisely the kind of regression an extended check (assert claimed ports/commands against source) would catch. Docs are load-bearing here — they are the agents' onboarding — so doc drift converts directly into wasted agent runs.
- **Effort:** 0.25 days (a tiny `docs-ci.yml` on `docs/**` + `**/CLAUDE.md` + `README.md` running `node scripts/check-docs.mjs`; add a port-claim assertion while there).
- **Autonomy:** High.
- **Null-option cost:** Drift accumulates silently until an agent acts on a stale claim; the FORBIDDEN list stops growing because it's invisible.

### DX-005 — No format/lint autofix rail: zero formatter config repo-wide, no hooks, and android CI runs no lint at all
- **Severity:** Medium · **Confidence:** [Certain]
- **Evidence:** No `.husky`/`lefthook`/`pre-commit` at root; no active `.git/hooks`; `grep -rn "detekt|ktlint|spotless" android/build.gradle.kts android/build-logic` → nothing; no `web/.prettierrc*`/`prettier.config.*`; `web/package.json` has no prettier/lint-staged/husky deps. Web CI does run `pnpm lint` + `pnpm typecheck` (`.github/workflows/web-ci.yml:43-47`). Android: `android/CLAUDE.md:96-99`: "CI does **not** run `lintRelease`; it currently reports pre-existing `MissingPermission` errors … Don't treat those as your regression" — a known-red lint baseline, so lint is unusable as a gate.
- **Impact:** The solo maintainer is the style/consistency gate for every agent diff across three ecosystems. Agents cannot self-verify formatting; the known-red android lint means genuine new lint errors are indistinguishable from the baseline — a classic agent trap explicitly worked around in prose instead of fixed with a baseline file (`lint.baseline` is a one-flag feature).
- **Effort:** 1.5 days (spotless+ktlint on android with a generated lint baseline so `lintDebug` gates in CI; prettier + a `format` script on web; optional pre-push hook).
- **Autonomy:** High — mechanical; large-but-inert first formatting commit.
- **Null-option cost:** Continuous low-grade review burden and style drift; every future agent re-reads the "ignore those lint errors" folklore.

### DX-006 — Churn×size hotspots: the files agents edit most are 1,000–2,700 lines
- **Severity:** Medium · **Confidence:** [Certain] (metrics) / [Likely] (cost attribution)
- **Evidence:** `wc -l` top offenders vs. 2026 change counts (`git log --since=2026-01-01 --name-only`):
  - `android/feature-workouts/.../session/WorkoutSessionScreen.kt` — **2,721 lines, 23 changes**
  - `android/feature-nutrition/.../NutritionTodayViewModel.kt` — **997 lines, 32 changes** (highest churn in the repo)
  - `android/core-data/.../nutrition/NutritionRepository.kt` — **1,007 lines, 29 changes**
  - `backend/.../api/nutrition/NutritionController.java` — **1,248 lines, 18 changes**; `web/components/workouts/WorkoutProgramProposalCard.tsx` — 1,433 lines.
- **Impact:** These are the intersection of "most likely to be in any given task" and "most expensive to load, reason about, and merge." For agent workflows this is a direct token/context tax and the main source of `old_string` edit collisions and rebase conflicts. Naming/navigability is otherwise good (package-by-feature on all three platforms; backend nutrition repos are per-concern — `FoodEntryRepository`, `SavedMealRepository`, etc. — not a name pileup).
- **Effort:** 3 days total across the top three (e.g., extract WorkoutSessionScreen's sub-composables into sibling files; split NutritionTodayViewModel by capture/log/adjust concern), done opportunistically per file when next touched.
- **Autonomy:** Medium — pure refactors an agent can do, but each needs the operator's regression appetite since nutrition/workout-session are the hottest product areas.
- **Null-option cost:** Compounding: churn keeps landing in these files, so they grow, and every future change pays more.

### DX-007 — The worktree bootstrap dance is manual, and the node_modules symlink escapes .gitignore
- **Severity:** Low · **Confidence:** [Certain]
- **Evidence:** Fresh worktrees need: `android/local.properties` recreated (`android/CLAUDE.md:68-70`: "this file is **gitignored**, so a fresh worktree has none — create it") + the `webOauthClientId` cache re-seeded (`android/app/build.gradle.kts:302-308` persists it to local.properties) + a `web/node_modules` symlink to the main checkout (present in this worktree: `web/node_modules -> /Users/gte619n/Development/tesseta/web/node_modules`). That symlink shows as untracked (`?? web/node_modules` in git status) because `/.gitignore:36` is `**/node_modules/` — the trailing slash matches directories only, not symlinks. No `scripts/new-worktree.sh` exists despite the worktree convention being codified in `/CLAUDE.md:31-36`.
- **Impact:** Known recurring friction (each new agent worktree breaks the android build until hand-fixed); the un-ignored symlink is git-status noise and a `git add -A` hazard for agents (harmless-but-embarrassing committed symlink to a local absolute path).
- **Effort:** 0.5 days: `scripts/new-worktree.sh` that runs `git worktree add`, copies `android/local.properties`, symlinks `web/node_modules`; change the ignore pattern to `**/node_modules` (no slash).
- **Autonomy:** High.
- **Null-option cost:** A few minutes lost per worktree, forever; occasional dirty-status confusion in agent sessions.

### DX-008 — Prod PHI is mirrored into the dev database by design, with merge (not wipe) semantics
- **Severity:** Medium · **Confidence:** [Certain] (mechanism) / [Guessing] (frequency of use)
- **Evidence:** Local dev correctly avoids prod: `infra/scripts/dev.sh:90-93` "Local dev intentionally hits the (default) database — keeps experimental data out of production." But `infra/scripts/copy-production-to-default-firestore.sh:1-12` mirrors the `production` DB "DOWN into the `(default)` … database that local dev reads," and "Import is a MERGE … docs that exist ONLY in `(default)` … are left in place" — so once pulled, prod PHI persists in the dev DB indefinitely, plus an export copy under `gs://health-fitness-160-firestore-exports/production-to-default/<ts>` (`copy-production-to-default-firestore.sh:24-25`). One GCP project for both (`deployment.md:44-46`), so IAM separation between "dev data" and "prod data" is database-name-deep.
- **Impact:** Debuggability is genuinely good (this is how you repro prod issues locally), but under REGULATED MODE the DX convenience means real health data lives in the experimentation DB and in GCS export folders with no documented retention/cleanup. Cross-domain: privacy/compliance should own the disposition; DX owns the alternative.
- **Effort:** 1–2 days for a scrub option (`--user <uid>` single-account pull, and/or a cleanup step that deletes the GCS export after import + a documented "reset (default)" cadence).
- **Autonomy:** Medium — script changes are agent-safe; policy call is the operator's.
- **Null-option cost:** Growing unaccounted PHI copies; audit exposure disproportionate to the convenience gained.

### DX-009 — The UAT harness (the repo's best repro rail) is manual-only
- **Severity:** Low · **Confidence:** [Certain]
- **Evidence:** `uat/README.md:1-16`: one command boots emulator + backend + web with a dev-login seam and deterministic AI stubs — "No GCP credentials, no Gemini key … everything is localhost and reset-able." - **Autonomy:** High.
- **Null-option cost:** Integration bugs surface in prod (post-merge) instead of overnight.

### DX-010 — Inner loops: android is excellent (roadmap's cheap wins shipped); backend has no hot-reload story; two S-effort roadmap items still on the table
- **Severity:** Low · **Confidence:** [Certain]
- **Evidence:**
  - Android (good): `android/gradle.properties:6-13` — config cache + parallel + caching + sized daemons all on; `docs/plans/android-build-speed-roadmap.md:11-28` — shipped: per-build `gcloud secrets` exec eliminated (cached in local.properties), CI split into parallel test/release jobs, setup-gradle caches, Cloud Build GCS cache tarball; measured "no-op 439ms, one-file incremental 2s, clean-ish assembleDebug 39s" (roadmap:16-18). Web: `dev.sh:167` runs `next dev --turbopack` (fast refresh). 
  - Roadmap remaining, by its own sequencing table (roadmap:177-185): §6 config-cache persistence in GHA (S effort, needs one repo secret, "~30-60s/warm CI run") and §1 custom Cloud Build builder image (S, "1-2 min/release, kills flaky installs") are the two still-cheap wins; §4 toolchain upgrade (AGP9/Kotlin 2.4/KSP2) is the large gateway item; §2/§3/§5/§7 should wait for timing data as the doc itself says.
  - Backend (gap): `grep -n devtools backend/build.gradle.kts` → nothing; the only documented loop is full `./gradlew bootRun` restart (`backend/README.md:8-10`). No `bootRun` JVM hot-swap, no devtools restart-on-compile.
- **Impact:** Backend edit-test is the slowest loop of the three for UI-adjacent iteration; agents (and the operator) pay a full boot per change. Counterweight: the emulator-tagged test split (`backend/build.gradle.kts:112-141` — unit tests exclude `firestore-emulator` tags so `./gradlew test` "stays fast and needs no external processes", with `CI=true` flipping required-mode) is a model agent-friendly design.
- **Effort:** 0.25 days to trial `spring-boot-devtools` (dev-only scope); the two S roadmap items are 0.5 day each.
- **Autonomy:** High.
- **Null-option cost:** Seconds-per-iteration ×every backend change; two documented, pre-analyzed CI wins keep not happening.

For an operator who works through AI agents, squatting this filename with non-instruction content is a small landmine.

- **Autonomy:** High.
- **Null-option cost:** Near-zero until a non-Claude agent is used; then confusing sessions with no obvious cause.

## Clean-clone verdict (domain brief §1)

- **backend/web only:** productive in <1h — [Likely]. Prereqs are discoverable (`web/package.json:48` pins `packageManager: pnpm@10.32.1`; Node 22 stated in README; JDK 21 via android/CLAUDE.md; `android/local.properties.example` exists so `android/README.md:18`'s `cp` instruction works; OAuth client ID self-bootstraps from Secret Manager after `gcloud auth login` per `android/CLAUDE.md:71-76`).
- **full dev.sh stack:** not in <1h on a truly fresh machine — [Certain] mechanism: Tailscale install + tailnet login + admin-console HTTPS-cert enablement + ADC login are all required (`dev.sh:17-22,44,150-154`) and none are in the quickstart docs (DX-003).

## THE THREE CHANGES (max maintenance-burden reduction, ranked)

1. **Make deploy failures push, not pull, and commit the observability runbook** (DX-001 + DX-002's PR-time Trivy). One Pub/Sub-driven notification + one `docs/reference/observability.md` + one Trivy CI job removes the single largest recurring operational tax and the biggest agent blind spot. ~2 days.
2. **Wire the existing machine-checks into CI and add the missing autofix rail** (DX-004 + DX-005): run `check-docs.mjs` on every docs/CLAUDE.md change, add prettier + ktlint/spotless + an android lint baseline so agents self-verify and CLAUDE.md folklore ("ignore those lint errors") can be deleted. ~2 days.
3. **Shrink the churn hotspots and bank the two S-effort build wins** (DX-006 + DX-010): split `NutritionTodayViewModel`/`NutritionRepository`/`WorkoutSessionScreen` when next touched; land roadmap §6 (GHA config-cache secret) and §1 (custom builder image). This cuts the marginal cost of *every future change* where changes actually happen. ~4 days spread.
