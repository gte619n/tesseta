# D6 — Cross-Platform Consistency (XPLAT)

Auditor: D6 · Date: 2026-09-13 · Scope: web (Next.js SSR) / android phone / android wear / backend (Spring Boot SSOT). REGULATED MODE: privacy scope respected — no user data or secrets in this report.

## BLUF

The platforms agree on more than expected — the portion-scaling duplication is explicitly mirrored and commented on both sides, the meds "today" endpoint has a correct timezone contract, and `docs/reference/feature-catalog.md` is ~90% accurate. The two structural failures are: **(1) the nutrition day key is computed three different ways** — web anchors "today" in UTC (`toISOString()` in a server component), android anchors in device-local time, and the backend's recent-meals anchor uses server-zone `LocalDate.now()` — so the same dinner logged at 8pm ET from web vs phone lands on *different* `nutritionDays` documents, silently corrupting daily totals; the codebase already contains the correct pattern (meds `?date=` + `X-Timezone`) and nutrition just doesn't use it. **(2) There is no client-version negotiation of any kind** against a continuously-deployed backend: the first-party API is unversioned (`api/...`; `/v1/**` is the third-party platform surface), there is no min-version gate, no in-app update path, and android's reflective Moshi setup means a renamed/removed server field backing a non-null Kotlin property is a runtime `JsonDataException` on every stale Play-store client with no recovery path. Secondary: the medication scheduling rule is duplicated phone-side despite a backend comment claiming it is the "one source of truth", with a real edge divergence (negative cycle offsets); the android composite-macro rescale diverges from the backend on calorie-only ingredients; web's TS types misstate nullability with zero runtime validation; and the feature catalog is missing the entire Drinks feature.

## Findings

### XPLAT-001 — Nutrition "today" is computed three different ways; web logs evening meals onto the wrong day
- **Severity:** Critical · **Confidence:** [Certain] on code; [Likely] on prod impact (prod server = UTC per two in-repo comments)
- **Evidence (all three sides):**
  - **Web (UTC):** `web/app/me/nutrition/page.tsx:40-42` — `// Helpers for date navigation (server-side only)` / `function today(): string { return new Date().toISOString().split("T")[0] ?? ""; }`. `toISOString()` is always UTC; this is a server component (`export const dynamic = "force-dynamic"`, page.tsx:38) so it runs on the Next server regardless. That date string becomes the `{date}` path segment for reads *and writes*. Also `page.tsx:128` — `mealForHour(new Date().getHours())` infers the meal chip from the **server's UTC hour**.
  - **Android (device-local):** `android/feature-nutrition/.../NutritionTodayViewModel.kt:58` — `val date: LocalDate = LocalDate.now(),`; entries POST to `api/me/nutrition/{date}/entries` (`android/core-data/.../nutrition/NutritionApi.kt:39`) with that local date.
  - **Backend (server-zone):** `backend/.../api/nutrition/NutritionController.java:861` — `nutrition.listRecentEntries(userId, LocalDate.now(), boundedDays)` (recent-meals anchor, used by both clients' one-tap recents); also `:123` (`LocalDate end = to != null ? to : LocalDate.now();`) and `:136` (`/today` endpoint). None of these read `RequestTimeZone`; grep confirms `X-Timezone`/`RequestTimeZone` is consumed only by `WorkoutProgramController.java`, `TodaysDosesController.java`, `RequestTimeZone.java`.
  - **The infrastructure exists and is ignored here:** android attaches the header to *every* request — `android/core-data/.../net/TimeZoneInterceptor.kt:18` — `.header("X-Timezone", ZoneId.systemDefault().id)`, with the comment (:9-10): "The server clock is UTC, so without this an evening workout for a user behind UTC lands on tomorrow." Web mirrors it: `web/components/TimezoneCookie.tsx:5-9` ("without this … 'today' endpoints … would roll over at the wrong local midnight") → forwarded in `web/lib/api.ts:73-87`. Meds does it correctly: `TodaysDosesController.java:43-47,55` — "'Today' is the caller's local date: an explicit `?date=` wins (the phone passes it), otherwise it's derived from the `X-Timezone` header".
- **Impact:** For a US-Eastern user, any meal logged on web after 7/8pm local lands on the UTC *next-day* `nutritionDays` document: web shows it under tomorrow, android (local-day) shows today as missing it; daily calorie/macro totals are wrong on both, silently, in a regulated health-data app. Recent-meals dedup window also shifts a day at UTC midnight. This is the same bug class the repo already diagnosed and fixed for workouts/meds — nutrition was skipped.
- **Effort:** 1–2 days (web: derive `today()` from the `tz` cookie; backend: thread `RequestTimeZone.resolve` through `NutritionController`'s three `LocalDate.now()` sites; android already correct).
- **Autonomy:** High — pattern to copy exists in-repo (`TodaysDosesController`).
- **Null option cost:** Every evening web log is misdated forever; cross-device totals never reconcile; erodes trust in the nutrition ledger.
- **Prompt:** "In tesseta: web/app/me/nutrition/page.tsx computes today() via new Date().toISOString() (UTC) and backend NutritionController.java uses LocalDate.now() at lines 123/136/861 without RequestTimeZone, while android uses device-local LocalDate.now() and TodaysDosesController.java:50-56 shows the correct ?date=/X-Timezone pattern. Make the nutrition day key caller-local everywhere: web derives today() from the tz cookie (see web/lib/api.ts:73-87), backend NutritionController resolves LocalDate.now(RequestTimeZone.resolve(header)). Add a test for an 8pm America/New_York log."

### XPLAT-002 — No client-version negotiation or forced-upgrade path; stale Moshi clients hard-crash on field rename
- **Severity:** High · **Confidence:** [Certain] on absence (searched backend for `User-Agent`/`X-App-Version`/`minVersion`/`clientVersion`; android for `AppUpdateManager`/Play Core/remote-config gates; wear for protocol constants — none found)
- **Evidence:**
  - First-party API is **unversioned**: `android/core-data/.../nutrition/NutritionApi.kt:36-45` — `@GET("api/me/nutrition/{date}")`, `@POST("api/me/nutrition/{date}/entries")` … The `/v1/**` controllers (`backend/.../api/v1/V1NutritionController.java:30` `@RequestMapping("/v1/nutrition")`) are the **third-party OAuth platform API** (ADR-0020, per `TodaysDosesController.java:22-24` "shared with the third-party GET /v1/doses"), not a client version rail.
  - Android JSON: `android/core-data/.../net/NetworkModule.kt:46-53` — `Moshi.Builder()…add(KotlinJsonAdapterFactory()).build()`. Additive server fields are silently ignored (safe), **but** a renamed/removed server field behind a non-null, no-default Kotlin property — e.g. `android/core-data/.../medications/MedicationDtos.kt:74` `val status: String,`, `:75` `val dose: Double,` — throws `JsonDataException` at parse time on every request.
  - No upgrade lever: `versionCode` is read only for the settings screen (`android/app/.../di/SettingsAppModule.kt` — `override val versionCode: Int = BuildConfig.VERSION_CODE`), never sent to or checked by the server.
  - Wear↔phone Data Layer messages carry no schema/protocol version: `android/wear/.../auth/PhoneTokenSyncService.kt:16` — `const val PATH_ID_TOKEN = "/auth/id-token"`, payload is a bare UTF-8 string (:23); `RefreshRequestPublisher.kt:15` — `"/auth/refresh-request"`.
- **Impact:** Backend deploys on every merge to main; Play-distributed APKs lag by days-to-weeks. Any non-additive contract change bricks stale clients with an unrecoverable parse crash and no "please update" screen — the failure mode is indistinguishable from an outage. Today this is mitigated only by discipline (nullable-with-default DTO fields), which nothing enforces.
- **Effort:** 2–3 days for a minimum viable rail: android sends `X-App-Version`; backend gains a `min-supported-version` property returning a typed 426; android maps it to a blocking upgrade screen. Wear: add a version int to the token message payload (1 hr).
- **Autonomy:** High.
- **Null option cost:** Acceptable *only while* every DTO change stays additive-and-nullable; one rename during a refactor (this branch is literally `tesseta-refactoring`) = fleet-wide crash loop.
- **Prompt:** "In tesseta: add minimal client-version negotiation. Android OkHttp interceptor (next to core-data/net/TimeZoneInterceptor.kt) sending X-App-Version: BuildConfig.VERSION_CODE; Spring filter comparing against app.min-supported-android-version returning 426 with a JSON body; android auth/network layer maps 426 to a full-screen 'update required' state. Do not touch /v1/** (third-party platform API). Include a version int in the wear /auth/id-token payload (PhoneTokenSyncService.kt:16)."

### XPLAT-003 — Medication scheduling rule duplicated phone-side despite backend's "one source of truth" claim; cycle edge diverges
- **Severity:** Medium · **Confidence:** [Certain] on duplication; [Likely] on the concrete edge divergence
- **Evidence (both sides):**
  - Backend claims singularity: `backend/.../core/medication/TodaysDosesService.java:19-20` — "one source of truth for the frequency / day-of-week / cycle scheduling rule rather than duplicating it." Cycle rule (:117-122): `long daysSinceStart = ChronoUnit.DAYS.between(startDate, today); int cycleLength = (onWeeks()+offWeeks())*7; long dayInCycle = daysSinceStart % cycleLength; yield dayInCycle < onWeeks()*7L;`
  - Android duplicates it for offline reminders: `android/core-domain/.../medications/ReminderPlanner.kt:23-44` — `fun isDueOn(med, date)` with `FrequencyType.CYCLE -> { val weeksSinceStart = ChronoUnit.WEEKS.between(cycle.startDate, date); if (weeksSinceStart < 0) return false; …}`, feeding `OutstandingDoses.scheduledFor` (`OutstandingDoses.kt:27-49`) and the whole reminder engine.
  - Divergence: for `date` **before** `cycle.startDate`, android returns `false` (explicit guard, ReminderPlanner.kt:40) while backend's Java `%` yields a negative `dayInCycle`, and `negative < onWeeks*7` is `true` → backend says **due**. For non-negative offsets the day-modulo vs week-modulo forms are mathematically equivalent, so steady-state agrees.
- **Impact:** A cycle med whose `cycle.startDate` is set in the future shows as due on web/backend "today's doses" but android reminders stay silent (or vice-versa after an edit) — exactly the class of "dashboard disagrees with phone" confusion already logged for meds in this repo. The duplication itself is *forced* (offline reminders can't call the server), but nothing (no shared test vectors) keeps the two implementations aligned.
- **Effort:** 0.5 day: fix the backend negative-offset guard; 1 day: add a shared JSON test-vector file exercised by both a JUnit test (backend) and a kotlin test (core-domain).
- **Autonomy:** High.
- **Null option cost:** Low day-to-day; a latent trap each time frequency semantics get extended (MONTHLY clamping — android ReminderPlanner.kt:34-36 — needs verification backend-side, see HYPOTHESES).
- **Prompt:** "In tesseta: TodaysDosesService.java:117-122 (day-modulo cycle rule, no negative guard) and ReminderPlanner.kt:23-44 (week-modulo, guarded) both implement med due-ness. Add a backend guard `if (daysSinceStart < 0) yield false;`, then create shared test vectors (JSON: med config + date → due?) consumed by tests on both sides, covering CYCLE pre-start, MONTHLY day-31 clamp, WEEKLY empty-days."

### XPLAT-004 — Duplicated composite-portion rescale diverges on null macros / calorie-only ingredients
- **Severity:** Medium · **Confidence:** [Likely] (formulas [Certain]; frequency of calorie-only composite ingredients in prod unverified)
- **Evidence (both sides):**
  - Backend: `backend/.../core/nutrition/NutritionService.java:983-988` — `Macros total = Macros.zero(); for (…) total = total.plus(ing.macros()); return total.scale(portion).withDerivedCalories();`. `Macros.plus`/`scale` **zero-fill nulls** (`Macros.java:21-23` `nz`, `:38-47` "Scales every component by factor, treating null as zero"), and `withDerivedCalories()` (`Macros.java:62-70`) **recomputes calories = 4·p + 4·c + 9·f**, keeping supplied calories only "When protein, carbs and fat are ALL null" — which after `zero()`+`plus()` they never are.
  - Android (deliberate mirror, local-only write): `android/core-data/.../nutrition/NutritionRepository.kt:979-990` — "Mirrors the backend's `NutritionService.compositeTotal` so an offline portion edit computes the same total the server would" — `sumMacros(...).scaleBy(portion)` where `scaleBy` **preserves nulls** (`caloriesKcal?.let { it * factor }`) and **scales stored calories linearly with no re-derivation**. The patch itself "is a pure local mirror write (offline-first, never a REST round-trip)" (`NutritionRepository.kt:238-245`).
- **Impact:** For all-macro ingredients the two agree (Atwater derivation is linear). They diverge when a composite contains a calories-only ingredient (all macros null) — a case the backend explicitly supports for single entries ("a calories-only quick add (e.g. a drink)", `Macros.java:56-60`) and that the drink work (alcohol kcal folded into `caloriesKcal`, no macro backing) makes more likely: android keeps those kcal scaled; the backend's rescale **zeroes them out**. Result: the phone shows one calorie total offline, the server's next recompute shows another — a "portion sizes are wrong again" regression-in-waiting on the exact code path already patched once (portion-sizes branch).
- **Effort:** 1 day — decide the semantic (preserve calorie-only kcal is the user-correct one), fix `compositeTotal` on the side that's wrong, add a two-sided fixture test.
- **Autonomy:** Medium — needs a product decision on which semantic wins.
- **Null option cost:** Sporadic cross-device calorie mismatches on composites containing quick-add/alcohol components; hard to reproduce, corrosive to trust.
- **Prompt:** "In tesseta: NutritionService.java:983-988 (compositeTotal → scale (null→0) → withDerivedCalories, dropping calorie-only ingredient kcal) vs NutritionRepository.kt:979-990 (null-preserving linear scale of caloriesKcal). Pick one semantic for composites containing all-null-macro (calorie-only, e.g. alcohol) ingredients — recommend: carry calorie-only kcal through the rescale server-side — align both, and add a shared fixture: composite of {chicken 300kcal from macros} + {whiskey 100kcal, null macros} at portion 0.5."

### XPLAT-005 — Web types silently under-model the wire contract (missing `adjustment`, wrong nullability), with zero runtime validation
- **Severity:** Medium · **Confidence:** [Certain]
- **Evidence:**
  - Backend entry: `backend/.../api/nutrition/EntryResponse.java:30-52` includes `EntryAnalysisStatus analysisStatus, List<IngredientResponse> ingredients, … LeftoverDto leftover, AdjustmentDto adjustment` (the adjustment carries `saveAsMeal`, mirrored from `core/nutrition/MealAdjustment.java:24-30`).
  - Web entry: `web/lib/types/nutrition.ts:19-49` — has `leftover?: Leftover | null` but **no `adjustment` field at all**; header comment (:2) says "Mirror the backend REST contract — keep in sync when DTOs change."   - Nullability lie: `nutrition.ts:23-25` declares `servingLabel: string; servingGrams: number;` non-null while `EntryResponse.java:36-37` has nullable `String servingLabel, Double servingGrams` (manual quick-adds omit them). No zod/runtime validation anywhere in `web/lib` — responses are blindly cast (JSON.parse + TS assertion).
  - Cross-check (prior-bug class now fixed android-side): android domain **does** carry it — `android/core-domain/.../nutrition/Nutrition.kt:504-510` `data class MealAdjustment(… val saveAsMeal: Boolean = false, …)` on `Entry.adjustment` (:178) — i.e., the #245 review-gap is closed on this branch for android, open for web.
  - Tolerance asymmetry for contract drift: android Moshi ignores unknown fields (NetworkModule.kt:46-53, no `failOnUnknown`); web ignores by construction; backend's default Spring mapper rejects unknown client-sent properties unless per-class relaxed (`backend/.../config/JsonSupport.java:41-44` builds a separate `LENIENT` mapper with `FAIL_ON_UNKNOWN_PROPERTIES, false` — the default `WEB` mapper at :36-39 does not).
  - Related skew (third-party surface): `backend/.../core/workoutprogram/LoggedSet.java:25-34` has 8 fields incl. `rir`/`rirSource`; the platform DTO `V1WorkoutsController.java:266-268` exposes 6 (drops both); android's `WorkoutProgramDto.kt:135-146` round-trips all 8 as nullable. - **Impact:** Web renders `undefined` where it typed `string`/`number` (NaN-ish UI on quick-add entries), and async Adjust state is invisible at web review — same class as the memory-logged saveAsMeal gap. Because nothing validates at runtime, drift is only discovered visually.
- **Effort:** 1 day (add `adjustment` to web Entry + fix nullability); +1–2 days if adding zod parsing at the `apiFetch` boundary for the nutrition module as a template.
- **Autonomy:** High.
- **Null option cost:** Continued silent drift; each backend DTO addition requires remembering three manual mirrors.
- **Prompt:** "In tesseta web/lib/types/nutrition.ts: (1) add `adjustment?: { status; instruction?; saveAsMeal; proposal? } | null` to Entry mirroring backend EntryResponse.java:52/MealAdjustment.java and render at least a badge in components/nutrition/NutritionMeals; (2) make servingLabel/servingGrams nullable to match EntryResponse.java:36-37 and fix resulting compile errors; (3) optionally introduce zod schemas for the nutrition API responses parsed inside lib/nutrition-api.ts."

### XPLAT-006 — Offline semantics: android has a durable outbox rail; web has nothing, and dead FCM makes the mirrors drift for hours
- **Severity:** Medium · **Confidence:** [Certain] on code; [Certain] on FCM-dead context (prior diagnosis)
- **Evidence (both sides):**
  - Android: full offline write rail — `android/core-data/src/main/java/com/gte619n/healthfitness/data/sync/` (`OutboxRepository.kt:38,89 suspend fun enqueue`, `OutboxReducer.kt:33`, `SyncWorkers.kt:75 OutboxDrainWorker`), plus nutrition durable ops (`NutritionRepository.kt:329-336 enqueueAdjustMeal`, `:625-632 enqueueDescribeAsync`); local patches are mirror-writes that never hit the network (`NutritionRepository.kt:238-245`).
  - Web: zero offline story — no service worker (`grep -ri offline web/` yields only OAuth `access_type: "offline"` hits, e.g. `web/app/me/profile/page.tsx:72`); every page is SSR (`web/app/me/nutrition/page.tsx:38 export const dynamic = "force-dynamic"`); a failed backend call throws to the route error boundary — `web/app/error.tsx:5-21` renders a generic `<ErrorState onRetry={reset} />` and `console.error`s.
  - Error-surface divergence: android nutrition surfaces failures inline/snackbar per-op (e.g. `feature-nutrition/.../NutritionCaptureViewModel.kt`, `DrinkCard.kt` carry Snackbar plumbing); web collapses any error — offline, 500, expired session — into the same retry card with no taxonomy. There is no shared error-code contract consumed by both clients.
  - Convergence dependency: cross-device convergence relies on FCM silent wakeups, which are dead in prod (cert mismatch — known context), so an action taken on web is invisible on the phone until a foreground pull.
- **Impact:** The same user action ("log a meal") has opposite failure behavior per platform: android silently queues and succeeds later; web hard-fails a whole page. Combined with XPLAT-001, a web-evening log is both *misdated* and *late-arriving* on the phone. Divergent error UX also means support/self-diagnosis reports aren't comparable across platforms.
- **Effort:** Not proposing web offline parity (SSR choice is reasonable). 1 day: differentiate web error boundary (offline vs 401 vs 5xx) and inline per-action failures on the nutrition page instead of throwing.
- **Autonomy:** High for the error-surface piece.
- **Null option cost:** Acceptable if FCM cert fix ships (restores timely convergence); the divergent error UX remains a paper cut.
- **Prompt:** "In tesseta web: server actions in app/me/nutrition/page.tsx currently let apiFetch failures throw to app/error.tsx (generic ErrorState). Return typed { ok:false, code } results from the nutrition mutations and render inline failure states in components/nutrition/*, distinguishing network-unreachable vs 401 vs 5xx. Keep the boundary as last resort."
