# D10 — Testing & Verification Baseline (TEST)

Audit date: 2026-09-13. Method: static reading + counts only (R3 — no suites executed). CI timings read from GitHub Actions run metadata via `gh` (read-only).

## BLUF

The unit-test net is better than the solo-founder stereotype — 860 backend @Test (all Java/Mockito, incl. a real Firestore-emulator tier), 579 android @Test with genuinely strong sync coverage (pull/LWW/tombstone/cursor/outbox-reducer all unit-tested, plus regression tests for the slash-alias and newline-secret prod bugs), and specific regression tests exist for the webhook "probe" misparse and token family-burn. But the net has four structural holes: (1) **zero API-layer cross-user isolation tests** in a privacy-regulated app — one repo-level scoping test is the entire tenant-isolation story; (2) **tests do not gate deploys** — merge-to-main deploys via Cloud Build regardless of CI, and the only end-to-end journeys (5 instrumented android files, the 22-file Selenium UAT harness) run in **no** automation, with UAT untouched since 2026-06-05; (3) **no contract tests** between backend JSON and android Moshi / web TS for the internal API (the field-drift class that already produced two prod sync bugs) — the platform /v1 API has exactly the right pattern (snapshot + oasdiff CI gate) and it was never applied inward; (4) **wear and web-UI have effectively no net at all** (wear: 0 tests; web e2e: 2 unauthenticated smoke tests). Refactoring safety is therefore very uneven per module — see the table and blunt statements below.

## Findings

### TEST-001 — No API-layer cross-user isolation tests in a privacy-regulated multi-user backend
- Severity: **Critical** | Confidence: [Certain]
- Evidence: Enumerated every distinct `subject("...")` literal per backend test file — no test file authenticates as two different users (script result: zero files with >1 distinct subject). All `status().isForbidden()` assertions are admin-role checks in one file (backend/src/test/java/com/gte619n/healthfitness/admin/AdminEquipmentControllerTest.java:89,111,139,179,230,249). SecurityConfigTest.java:20-84 tests only route classification (public/authenticated/denyAll), 85 lines total. The single tenant-isolation test in the entire repo is repo-level: backend/src/test/java/com/gte619n/healthfitness/persistence/goals/StepRepositoryScopingTest.java (emulator tier, goals steps only). Per-user scoping everywhere else rests on the untested convention that every service passes `CurrentUserProvider` userId into repo calls.
- Impact: A refactor that drops/forgets a `userId` filter in any controller→service→repo path (nutrition, medications, blood, workouts, body-comp) returns another user's health data and the whole 860-test suite stays green. REGULATED/privacy scope makes this the top testing risk; it also silently caps how aggressively any other domain can refactor backend services.
- Effort: 3-4 days (parameterized MockMvc harness: seed user A via API, request as user B, assert 404/403/empty across ~15 controllers; plus 5-6 more repo-scoping tests in the emulator tier).
- Autonomy: high (pure test additions). Null-option cost: every future backend change carries silent cross-tenant-leak risk with zero detection; in a breach, "no isolation tests existed" is indefensible.
- Prompt: "In backend/src/test, build a cross-user isolation suite: for each MockMvc controller test package (blood, nutrition, medication, workouts, bodycomposition, goals), add tests that create a resource as JWT subject A and then GET/PATCH/DELETE it as subject B, asserting 404/403/empty-list. Reuse TestPersistenceConfig in-memory repos (they key by userId). Model on SecurityConfigTest.java jwt() post-processor usage. Also clone persistence/goals/StepRepositoryScopingTest.java for nutrition entries, adherence, medications, blood readings in the firestore-emulator tier."

### TEST-002 — Tests gate nothing that ships: deploys fire on merge regardless of CI, and every end-to-end tier runs in no automation
- Severity: **Critical** | Confidence: [Certain] for repo facts; [Likely] for Cloud Build trigger semantics (operator memory "deploy-pipeline-observability": prod deploy = merge to main, CI doesn't gate deploys; corroborated by absence of any deploy job in .github/workflows/)
- Evidence: (a) .github/workflows/ contains only android-ci/backend-ci/web-ci/codeql/terraform-ci — no deploy step, no `needs:` chain to any deploy (verified file list + grep). (b) The three end-to-end tiers all run nowhere: android instrumented sync tests — android-ci.yml:71-74 runs only `testDebugUnitTest` + duplicate-class checks, no connectedAndroidTest job; SyncE2ETest.kt header comment: "None of this runs in a JVM unit test or in the agent sandbox. Run with: ./gradlew :core-data:connectedDebugAndroidTest"; uat/ Selenium suite — `grep -rn uat .github/workflows/ terraform` = 0 hits; playwright = 2 unauthenticated smoke tests (web/e2e/smoke.spec.ts:6,13). (c) Operator memory records a Jul-2026 stretch where deploys silently failed across multiple merges and nobody noticed — the same decoupling in the other direction.
- Impact: A red or skipped CI run does not stop a prod deploy; and even a green CI proves nothing end-to-end (no authenticated web journey, no device sync journey, no UAT). Combined with TEST-001, a cross-user regression could merge and be serving prod traffic ~10 minutes later with all lights green.
- Effort: 1-2 days (make Cloud Build triggers require the CI check via branch protection + required checks, or move deploy into a workflow with `needs: [test]`; add a nightly `connectedDebugAndroidTest` on an emulator runner ≈ 1 day more).
- Autonomy: medium (needs GCP/GitHub settings access, operator approval). Null-option cost: every other domain's "tests will catch it" assumption is false at the ship gate; repeat of the silent-red-main incident.
- Prompt: "Wire deploy gating: enable GitHub branch protection on main requiring android-ci/backend-ci/web-ci checks, and confirm the Cloud Build deploy-*-on-main triggers cannot fire on a commit whose checks failed (or convert deploys to GitHub Actions jobs with needs:). Separately add a scheduled workflow running :core-data:connectedDebugAndroidTest on ubuntu-latest with reactivecircus/android-emulator-runner, uploading the connected-test report."

- Autonomy: high. Null-option cost: DB migration regressions reach users' devices — the worst class of mobile bug (unrecoverable local data).

### TEST-005 — No contract tests for the internal API (backend JSON ↔ android Moshi ↔ web TS); the /v1 platform API proves the pattern exists in-house
- Severity: Medium (High-adjacent: this bug class has shipped twice) | Confidence: [Certain]
- Evidence: Android DTO tests parse hand-written JSON literals (core-data WorkoutSessionDtoTest.kt, EquipmentSpecMoshiAdapterTest.kt, NutritionAdjustParseTest.kt) — nothing generated from or checked against backend serialization. Web types are hand-maintained TS; no OpenAPI codegen for /api. Contrast: the third-party /v1 API has V1OpenApiSnapshotTest.java:32 ("asserts it byte-for-byte against the committed" spec) + backend-ci `openapi-breaking-change` job (backend-ci.yml:178-204, oasdiff `fail-on: ERR`). Prior prod bugs in exactly this gap: slash-collection alias miss ("food logged on web never reaches phone") and entryId round-trip ("meal-move PATCH 400") — both now have android-side regression tests but the class is unguarded.
- Impact: Any backend DTO/field rename or delta-payload shape change ships green and breaks sync/clients at runtime; android release lag means broken-prod windows.
- Effort: 3-5 days (springdoc-generate an internal /api spec + snapshot test mirroring V1OpenApiSnapshotTest + same oasdiff job; or golden-file JSON fixtures shared into android tests as a first increment).
- Autonomy: high. Null-option cost: recurring cross-device sync outages of the kind already logged twice; every DTO-touching refactor is a coin-flip.

### TEST-006 — TestPersistenceConfig fakes diverge from Firestore (no transactions/ordering) and several are silent no-ops
- Severity: Medium | Confidence: [Certain] for the code; [Likely] for concrete divergence-caused blind spots
- Evidence: backend/src/test/java/com/gte619n/healthfitness/testsupport/TestPersistenceConfig.java:56-60 self-describes two flavors, including "Empty stub… calling these methods from a test will return empty/no-op without failing" — MacroTargetRepository:440-446, DrugRepository:449-458, MedicationRepository:461-471, ProtocolRepository:473-481, AdherenceRepository:484-492, BloodTestReportRepository:517-525, DexaScanRepository:528-536 all `save(){}` / return-empty. A @SpringBootTest exercising a medication/adherence/DEXA write path against these stubs can "pass" while persisting nothing and asserting only status codes. None of the in-memory fakes model Firestore transactions, contention, or query ordering; those semantics are covered only by the 13 emulator @Test in 8 files (persistence/*ConcurrencyTest, StepRepositoryScopingTest, ScheduledWorkoutRange…). Churn hotspot: the config is @Import-ed by every @SpringBootTest (37 files) and grows a bean per feature.
- Impact: A refactor that changes transactional/read-after-write behavior in a Firestore repo is invisible to the 847 non-emulator tests; medication-domain controller tests are structurally weaker than they look.
- Effort: 2-3 days (promote medication/adherence stubs to real in-memory maps like FoodEntryRepository:343-381 already is; move 4-5 highest-risk repos into the emulator tier).
- Autonomy: high. Null-option cost: false confidence concentrated exactly in the medication domain (the app's most safety-sensitive data), plus growing bean-registration churn on every feature.

### TEST-008 — Known flake verified and contained: SyncEnginePullTest LWW case; Unconfined is the house style (16 test usages)
- Severity: Low | Confidence: [Certain]

## Blunt refactor-safety statements (verbatim format)

- If you refactored **SyncEngine** tomorrow, the core-data JVM suite (SyncEnginePullTest, OutboxDrainTest, OutboxReducerTest, CollectionRegistryTest — ~40 targeted tests incl. three prod-bug regressions) would catch most logic regressions in pull/LWW/tombstone/reducer/endpoint-routing; what would NOT be caught is anything at the Room-DAO/OkHttp/migration layer or true two-device convergence, because the tests that cover those (ConvergenceTest, SyncE2ETest, HfDatabaseInstrumentedTest) run in no CI — you'd have to remember `./gradlew :core-data:connectedDebugAndroidTest` yourself. Safest android module to refactor, with that one manual step.
- If you refactored **the backend nutrition service** tomorrow, NutritionServiceTest (incl. composite-portion 0.5× scaling), LeftoverMathTest/LeftoverServiceTest, MealAdjustmentServiceTest and NutritionJobControllerTest would catch math, replay-idempotency and job-auth regressions; what would NOT be caught: Firestore rollup/transaction behavior changes (one emulator test), any cross-user scoping mistake, and any DTO shape change as seen by android/web (no contracts) — those ship green.
- If you refactored **backend security config** tomorrow, SecurityConfigTest would catch route-classification regressions (a newly-public endpoint, a denyAll sweep, the describe-allowlist); what would NOT be caught is the far likelier failure — a per-user scoping regression anywhere below the filter chain. No test in the repo requests one user's data as another user at the API layer. Treat SecurityConfig + service-layer scoping as UNSAFE to refactor until TEST-001 lands.
- If you refactored **the web dashboard** tomorrow, essentially nothing would catch a regression: vitest covers lib/ pure functions and two UI atoms, playwright never signs in, and the UAT suite that does exercise the dashboard hasn't run since June. Only `tsc`/eslint stand between you and prod. UNSAFE to refactor beyond type-level changes.
- If you refactored **the wear app** tomorrow, nothing would catch a regression — zero unit tests, zero instrumented tests, and CI only checks duplicate classes; the surface is small (5 source files) but the net is literally empty. UNSAFE, mitigated only by module size.
