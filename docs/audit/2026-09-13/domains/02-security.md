# D2 — Security Audit (SEC)

Date: 2026-09-13. Auditor: D2 SECURITY. Repo: tesseta monorepo (worktree `sess_bef801a7…`).

## BLUF

The auth core is in better shape than typical for a solo project: the three-family JWT routing on an unparsed `iss` peek is **not** exploitable (each decoder is pinned to its own algorithm + key + issuer, and a `PlatformAudienceFilter` confines platform tokens to `/v1`) [Certain]; refresh tokens are stored hashed with constant-time comparison [Certain]; `ADMIN_EMAILS` fails closed to empty [Certain]; all `/api/admin/**` controllers carry class-level `@AdminOnly` [Certain]; production secrets are all env-refs resolved from Secret Manager, nothing literal is checked in [Certain]; `/api/me/**` horizontal scoping derives userId exclusively from the JWT `sub` [Certain]; web security headers (CSP, HSTS, X-Frame-Options DENY) are present [Certain].

The real exposures are economic and integrity-shaped, not classic breach-shaped: **(1)** open signup (any Google account auto-provisions) combined with **zero rate limiting on the Gemini-backed `/api` endpoints** makes API cost abuse trivially scriptable; **(2)** the global food catalog is mutable cross-user — any authenticated user can edit any drink entry and force image regeneration on any food; **(3)** the ADR-0019 refresh-token successor chain, by design, makes refresh-token theft *undetectable* — a stolen token stays usable indefinitely with no family burn; **(4)** the Withings webhook shared secret rides in a URL query parameter and therefore lands in Cloud Run request logs, violating the standing "no secrets in logs" requirement; **(5)** Android/Wear auth-token DataStores are not excluded from device backup while the DB is.

No finding rises to "breach/data-loss NOW" critical. 11 findings follow: 1 high, 6 medium, 4 low.

## Findings

### SEC-001 — No rate limiting or per-user quota on Gemini-backed endpoints with open signup
- **Severity:** high
- **Confidence:** certain
- **Evidence:**
  - Open signup: `backend/src/main/java/com/gte619n/healthfitness/auth/UserProvisioningFilter.java:32-34` — `if (auth != null && auth.isAuthenticated()) { users.provisionIfAbsent(currentUserProvider.get()); }` — every request bearing any valid Google ID token (any Google account, given the audience matches) provisions a user. [Certain]
  - The only rate limit in the backend is on the third-party `/v1` surface: `backend/src/main/resources/application.yml:119-121` — `rate-limit-requests: ${PLATFORM_RATE_LIMIT_REQUESTS:600}` / `rate-limit-window: ${PLATFORM_RATE_LIMIT_WINDOW:5m}`; `V1RateLimitFilter` is wired only after `V1AuditFilter` for `/v1` (`SecurityConfig.java:268`). No `@RateLimit`/bucket/counter exists on any `/api/**` controller (verified by domain-wide sweep). [Certain]
  - Gemini-triggering endpoints reachable by any provisioned user: `POST /api/nutrition/capture/meal`, `/capture/label` (`api/nutrition/NutritionCaptureController.java:45-73` — no size check in-controller beyond the Spring multipart cap), `POST /api/nutrition/describe` (`MealDescriptionController.java:41-57`), and `POST /api/foods/{foodId}/image/regenerate` (`FoodController.java:127-135`) which enqueues studio-image generation for **any** catalog food with no ownership check and no cooldown. [Certain]
  - Multipart cap is 30MB per request: `backend/src/main/resources/application.yml:7-14` — `max-file-size: 30MB`. [Certain]
- **Impact:** Anyone with a throwaway Google account can script unlimited 30MB photo captures and image-regeneration calls; spend is bounded only by Cloud Run autoscaling and the project's Gemini quota. Given the Aug-2026 Gemini-burn incident was ~an order of magnitude of real money on a sibling project, the billing exposure is concrete [Likely]. Also a availability risk: the nutrition-jobs queue (local threads 4, queue 500 — `application.yml` `NUTRITION_JOBS_LOCAL_*`) can be saturated, starving legitimate users. [Likely]
- **Effort:** 2 days
- **Autonomy:** agent-reviewed
- **Null option cost:** Unbounded Gemini/Cloud Run spend on a public endpoint; a single hostile or curious actor can generate a four-figure bill in a weekend [Guessing on magnitude, Certain on unboundedness].
- **Prompt:** In `backend/`, add a per-user fixed-window rate limiter (reuse the Firestore-backed `core/platform/PlatformRateLimitStore` pattern from `V1RateLimitFilter`) applied to `POST /api/nutrition/capture/**`, `POST /api/nutrition/describe`, `POST /api/foods/*/image/regenerate`, and the adjust/leftover endpoints. Key by JWT `sub`, defaults ~30 Gemini-triggering requests per user per hour, configurable via `app.gemini.rate-limit-*` properties with env-refs in `application.yml`. Additionally restrict `/api/foods/{id}/image/regenerate` to the food's `createdBy` or `@AdminOnly`. Constraints: do not touch `/v1` filters; return 429 with a Retry-After header; keep the limiter fail-open on Firestore errors (availability over enforcement) and log when it does. Verify with a `@SpringBootTest` slice: 31st capture in an hour → 429; different user unaffected.

### SEC-002 — Global food catalog is cross-user mutable (drink update, image regenerate, unmoderated creates)
- **Severity:** medium
- **Confidence:** certain
- **Evidence:**
  - `backend/src/main/java/com/gte619n/healthfitness/api/nutrition/DrinkController.java:42,137-152` — `@RequestMapping("/api/me/drinks")` … `@PutMapping("/{foodId}") public FoodResponse update(...)` calls `catalog.updateDrink(foodId, …)` with **no ownership check**; `userId` is used only for `syncNotifier.changed(...)`. [Certain]
  - `core/nutrition/FoodCatalogService.java:422-431` — `updateDrink` does `CatalogFood existing = get(foodId);` and rewrites name/ABV/macros, preserving `existing.createdBy()` — no comparison of caller to `createdBy`. [Certain]
  - `api/nutrition/FoodController.java:23` — `/** Global, authenticated (not user-scoped) food catalog API. */`; `:76-112` — any authenticated user creates `FoodSource.USER` entries into the shared catalog, immediately visible via `GET /api/foods/search` (`:39-42`). [Certain]
  - `FoodController.java:127-135` — `POST /{foodId}/image/regenerate` on any food, any user (also cited in SEC-001). [Certain]
  - `FoodCatalogService.java:537-566` — `confirm(foodId, userId)` counts distinct-user confirmations toward `verifiedAt` promotion; nothing stops sockpuppet accounts (open signup) from "verifying" a poisoned entry. [Certain]
- **Impact:** User A can silently rewrite the ABV/macros of a drink user B has saved and re-logs (future logs pick up corrupted values), can pollute search results with plausible-but-wrong foods, and can launder poison into "verified" status with a handful of throwaway Google accounts. For a self-declared PHI-grade nutrition product, this is a data-integrity hole in health data. [Likely]
- **Effort:** 1.5 days
- **Autonomy:** agent-reviewed
- **Null option cost:** Any multi-user rollout ships with a shared catalog that any account can corrupt; cleanup requires forensic diffing of `foodCatalog` history that Firestore doesn't keep.
- **Prompt:** In `backend/`: (1) in `DrinkController.update` and `FoodCatalogService.updateDrink`, enforce `existing.createdBy().equals(userId)` (403 otherwise), with an `@AdminOnly`-style admin override; (2) restrict `FoodController.regenerateImage` to creator-or-admin; (3) in `FoodCatalogService.confirm`, ignore confirmations from the creator and consider requiring account age / distinct verified-email heuristics before `verifiedAt` promotion (document the chosen rule). Constraints: Android relies on the drink update path (drink-logging branch, `catalog_cache`) — creator-scoped enforcement matches its UX (users edit their own drinks); don't break the sync notifier call. Verify with controller tests: non-creator PUT → 403; creator PUT → 200; admin PUT → 200.

### SEC-003 — ADR-0019 successor-chain refresh makes refresh-token theft undetectable (no reuse burn while session lives)
- **Severity:** medium
- **Confidence:** certain
- **Evidence:**
  - `backend/src/main/java/com/gte619n/healthfitness/auth/SessionTokenService.java:128-171` — `advanceChain`: a presented **revoked** (already-rotated) token walks `replacedBy` to the live tip and rotates it: "for a revoked (already-rotated) token it walks {@code replacedBy} to the live tip and rotates that, re-pointing the presented token forward." Family burn happens **only** when `liveTip(...) == null` (`:130-133`), i.e. logout-revoked, expired, dangling, or >64 hops. [Certain]
  - `SessionTokenService.java:157-161` — `store.repoint(presented.tokenId(), successorId)` re-points every honored stale token at the fresh tip, guaranteeing the *next* replay is also a single hop onto a live tip. [Certain]
  - `AppSessionProperties.java:18-21` — "Benign replays … are handled by the successor-chain walk … not a time window, so there is no grace-period knob." Refresh TTL: `:27` — `Duration.ofDays(60)`, sliding via rotation. [Certain]
- **Impact:** If an attacker exfiltrates any historical refresh token for a session (e.g. via the un-excluded Android backup in SEC-005, a device image, or the Wear relay), both attacker and victim refresh forever: each presents a revoked token, the chain walk honours it, and **the theft-detection property that rotation normally provides (reuse → family burn) never triggers**. The session is compromised silently and indefinitely (60d sliding, renewed on every use) until an explicit logout. This is a deliberate availability-over-detection trade (flaky-mobile lost-response retries), but as written the detection is not weakened — it is absent. [Certain]
- **Effort:** 1–2 days
- **Autonomy:** agent-reviewed (design decision needs operator sign-off on the tradeoff)
- **Null option cost:** Token theft on any device/backup vector converts to a permanent invisible session; no signal ever reaches the owner. Given a single-user install base today the live risk is small, but this is the primitive every other token finding compounds against.
- **Prompt:** In `backend/src/main/java/com/gte619n/healthfitness/auth/SessionTokenService.java`, bound the honour window for revoked-token replays without reintroducing the lost-response failure ADR-0019 fixed: honour a replay only if the presented token was rotated within a configurable grace (e.g. `app.session.replay-grace`, default 48h — covers offline phones) **or** cap the number of times a given tokenId may be re-pointed (add a counter to `StoredRefreshToken`); beyond that, burn the family and log a `refresh_replay_burn` event with userId (no token material). Update ADR-0019 with the chosen bound. Constraints: keep `MAX_CHAIN_HOPS`; never log token ids at INFO+; preserve existing tests in the session-token test suite and add: replay after grace → 401 + family revoked. Verify with unit tests around `refresh()`.

### SEC-004 — Withings webhook shared secret travels as a URL query parameter (lands in request logs)
- **Severity:** medium
- **Confidence:** certain
- **Evidence:**
  - `backend/src/main/java/com/gte619n/healthfitness/api/withings/WithingsWebhookController.java:24-26` — "there is no signature, so we authenticate by a shared secret carried as a `secret` query param on the registered callback URL"; `:87` — `@RequestParam(name = "secret", required = false) String secret`. [Certain]
  - Comparison itself is constant-time (`:137-149`) and fail-closed on blank config — good. [Certain]
  - Standing requirement: `docs/requirements/privacy-and-compliance.md` §6 "No PHI/tokens in logs" (per audit brief) — Cloud Run access logs record `httpRequest.requestUrl` including the query string, so every Withings notification writes the secret to Cloud Logging. [Likely — see HYPOTHESES H2 for confirmation method]
- **Impact:** The webhook secret is persistently disclosed to anyone with project log-read access and to any log sink/export. Blast radius is bounded by design — the handler re-fetches from Withings with the user's own OAuth token and "does not trust the webhook body's values" (`privacy-and-compliance.md:82-84` states this for Google Health; the Withings handler likewise only triggers `sync.importSleep/importBody` re-fetches, `WithingsWebhookController.java:126-129`) — so a leaked secret enables forged sync-triggers and probe traffic, not data injection. Still a direct violation of the no-secrets-in-logs requirement in regulated mode. [Certain]
- **Effort:** 0.5 day
- **Autonomy:** operator-required (needs Cloud Logging config + Withings callback re-registration)
- **Null option cost:** Ongoing accumulation of a live credential in logs; any future log-access grant (support tooling, BigQuery export) silently inherits it.
- **Prompt:** Two-part fix. (1) Infra: add a Cloud Logging exclusion or field-redaction for `requestUrl` on requests matching `/api/webhooks/withings` on the backend Cloud Run service (document in `infra/`); rotate `withings-webhook-secret` in Secret Manager afterward and re-register the Withings callback URL (Withings notify offers no custom headers, so the query param itself must stay — this is a platform constraint). (2) Backend: confirm nothing else logs the full request URL for this path (check any request-logging filters). Verify: send a probe POST with a dummy secret, confirm the query string is absent/redacted in Cloud Logging.

### SEC-005 — Android + Wear auth-token DataStores are not excluded from backup; Wear has no backup rules at all
- **Severity:** medium
- **Confidence:** certain
- **Evidence:**
  - `android/core-data/src/main/java/com/gte619n/healthfitness/data/auth/IdTokenCache.kt:25` — `private val Context.authStore by preferencesDataStore("hf-auth")` holding `id_token`, `refresh_token` (`:29-32`), plain (unencrypted) by design (`:21-23` comment). [Certain]
  - `android/app/src/main/res/xml/backup_rules.xml:9-10` and `data_extraction_rules.xml:18-25` exclude only `hf_offline_db_prefs.xml` and `hf-offline.db` — the DataStore file (`files/datastore/hf-auth.preferences_pb`) is **not** excluded from cloud-backup or device-transfer. [Certain]
  - Wear: `android/wear/src/main/java/com/gte619n/healthfitness/wear/auth/WearIdTokenCache.kt:10` — `preferencesDataStore("hf-wear-auth")`; `android/wear/src/main/res/xml/` does not exist and the wear manifest sets no `allowBackup`/`dataExtractionRules` (grep over both manifests found no `allowBackup`), so the platform default (backup enabled) applies. [Certain for absence of config; Likely for effective default]
  - Compounding: refresh tokens are 60-day sliding (`AppSessionProperties.java:27`) and theft is undetectable per SEC-003.
- **Impact:** Access + refresh tokens ride into Google cloud backups and device-to-device transfers. Auto-backup is E2E-encrypted with the lockscreen secret on modern Android [Likely], but device-transfer and any backup extraction path (e.g. `adb backup` on debuggable forks, OEM transfer tools) hand over a long-lived, silently-usable session credential — inconsistent with the care taken to exclude the (already-encrypted!) DB. ADR-0007's exclusion intent is only half-implemented. [Certain]
- **Effort:** 0.25 day
- **Autonomy:** agent-unattended
- **Null option_cost:** Token exfiltration via backup/transfer remains open; combined with SEC-003 it is a durable account compromise vector.
- **Prompt:** In `android/app/src/main/res/xml/backup_rules.xml` and `data_extraction_rules.xml`, add excludes for the DataStore file: `<exclude domain="file" path="datastore/hf-auth.preferences_pb" />` in `<cloud-backup>` and `<device-transfer>` (note: DataStore lives under domain `file`, NOT `sharedpref` — do not use the sharedpref domain). Create matching backup/data-extraction rule XMLs for the wear module excluding `datastore/hf-wear-auth.preferences_pb`, reference them from `android/wear/src/main/AndroidManifest.xml`, and set `android:allowBackup` policy explicitly on both manifests. Verify: `bmgr backupnow` on an emulator, restore to a second emulator, assert the app comes up signed-out.

### SEC-006 — Release builds (phone + wear) are signed with the checked-in public debug keystore
- **Severity:** medium
- **Confidence:** certain
- **Evidence:**
  - `android/app/build.gradle.kts:99-106` — `storeFile = file("../debug.keystore"); storePassword = "android"; keyAlias = "androiddebugkey"; keyPassword = "android"`; `:136` — release buildType: `signingConfig = signingConfigs.getByName("debug")` with an acknowledging comment (`:125-135`) "Switch to a private upload key (Play App Signing) before any Play Store release." [Certain]
  - `android/debug.keystore` is committed (`git ls-files` confirms; `android/.gitignore` has `!debug.keystore`). [Certain]
  - Wear release inherits the same config (`android/wear/build.gradle.kts:21-40`, no release signing override). [Certain]
  - `android/cloudbuild.yaml:4` — release APK built in CI is signed with this keystore. [Certain]
- **Impact:** The *production* app identity (for the current Firebase App Distribution install base) is signed by a key whose material and password are public in the repo. - **Autonomy:** operator-required (key ceremony + Firebase console + all testers must reinstall due to signature change)
- **Null option cost:** Every day extends the installed base bound to a public key; the eventual signature migration forces uninstall/reinstall for all testers, and the FCM outage persists until fingerprints are sorted anyway.
- **Prompt:** Create a private release keystore, store it (and passwords) in Secret Manager (`android-release-keystore`, `android-release-keystore-password`); in `android/app/build.gradle.kts` and `android/wear/build.gradle.kts` add a `release` signingConfig that resolves from env/Secret Manager (mirror the existing `WEB_OAUTH_CLIENT_ID` resolution pattern at `android/app/build.gradle.kts:248-331`), falling back to debug signing for local builds; update `android/cloudbuild.yaml` to fetch and use it; register the new SHA-1/SHA-256 in the Firebase Android app (fixes the FCM dead-push at the same time). Verify: CI-built APK's signing cert differs from `debug.keystore`'s; FCM Installations succeed on a device running the new build.

## Verified-safe (no finding, for the record)

- **`iss`-peek routing is not an algorithm-confusion vector.** `SecurityConfig.java:89-98` routes on the unverified issuer, but each branch is a pinned decoder: platform = RS256 + platform public key + issuer + audience validators (`:105-116`); session = HS256-only (`macAlgorithm(MacAlgorithm.HS256)`) with a ≥32-byte key enforced (`SessionTokenService.java:264-271`) sourced from Secret Manager (`application.yml` `${SESSION_SIGNING_KEY:}`, empty ⇒ disabled/503); fallback = Google JWKS + `GoogleAudienceValidator`.
