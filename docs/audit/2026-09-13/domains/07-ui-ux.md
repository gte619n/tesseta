# D7 — UI/UX Audit (prefix: UX)

Audited from code only (no running app). Date: 2026-09-13. Repo: tesseta monorepo (web/ Next.js 15, android/ Compose M3 + wear).

## BLUF

The design system is in excellent shape — 1,612 `Hf.*` token references vs only 9 raw `MaterialTheme.*` and 11 raw hex colors outside core-ui on Android; only 3 arbitrary hex values in the entire web tree. State coverage on Android feature screens is strong (loading/empty/error branches nearly everywhere). The real problems are: **(1) the Android meal-entry delete is a one-tap, no-confirm, no-undo destructive action** (the web equivalent confirms — the platforms contradict each other); **(2) medication names appear on the lock screen** — no notification in the app sets `setVisibility`, so all default to public (regulated-mode privacy issue); **(3) the web nutrition page silently renders a fetch failure as a zero-calorie "empty day"** — an outage is indistinguishable from "you ate nothing"; **(4) with FCM dead in prod (known cross-domain outage), the async Adjust/Leftovers review flows have no proactive completion signal** — the foreground settle-poll covers photo analysis for 4 minutes, but review-ready states only surface if the user happens to reopen the day view. Dark mode does not exist on any platform; i18n is effectively not started (fine for a solo product today, cost is growing linearly with string count).

## Findings

### UX-001 — Android meal-entry delete: one tap, no confirmation, no undo
- **Severity:** critical · **Confidence:** [Certain]
- **Evidence:** `android/feature-nutrition/src/main/java/com/gte619n/healthfitness/feature/nutrition/NutritionTodayComponents.kt:335-337` — `Box(modifier = Modifier.clickable(enabled = !pending) { onDelete() }…)` with `Icon(Icons.Outlined.Delete, contentDescription = "Delete entry"…)`; wired straight to the ViewModel at `NutritionTodayScreen.kt:95` — `onDeleteEntry = viewModel::deleteEntry`. Zero `ConfirmDialog`/`AlertDialog` matches in either file (verified by grep). Contrast web: `web/components/nutrition/MealSection.tsx:124-138` uses `useConfirm` — `title: "Remove food entry?"`, `tone: "danger"`. No undo snackbar exists for entries (the only undo snackbar in nutrition is drink logging, `DrinkCard.kt:121` "Added — Undo").
- **Impact:** An 18dp trash target sits on every entry row in a scrollable list; one mis-tap permanently destroys a photo-analyzed entry (Gemini-derived macros + image) that the user cannot reconstruct. This is the app's most-used screen. The two platforms contradict each other on the same action.
- **Effort:** 0.5 days · **Autonomy:** agent-solo · **Null-option cost:** ongoing silent data loss from mis-taps; erodes trust in logging accuracy ("didn't I log lunch?").
- **Prompt:** "In `android/feature-nutrition/.../NutritionTodayComponents.kt` the entry-row delete icon (`clickable { onDelete() }`, ~line 335) fires `NutritionTodayViewModel.deleteEntry` with no confirmation. Add the same confirm pattern used by `WorkoutSessionScreen.kt:363-371` (`ConfirmDialog`, destructive=true) with copy matching web's `MealSection.tsx:124-138` ('Remove food entry?'), or an undo snackbar like `DrinkCard.kt:121`. Keep the pending-spinner state behavior."

### UX-002 — All notifications default to lock-screen-public; medication names are PHI on the lock screen
- **Severity:** high · **Confidence:** [Certain]
- **Evidence:** `android/core-data/src/main/java/com/gte619n/healthfitness/data/reminders/ReminderNotifier.kt:59-71` — content lines are `"${it.name} — ${formatDose(it.dose)} ${it.unit} · ${it.time.format(timeFormat)}"` in an `InboxStyle`, `PRIORITY_HIGH`. **No `setVisibility(` call exists anywhere in the android tree** (grep: zero matches), so every notification is `VISIBILITY_PUBLIC`-equivalent on the lock screen. Same gap on meal notifications: `android/app/.../push/HfMessagingService.kt:140-145` (leftovers), `:200-209` (adjust) render server-supplied `notification.title/body` (meal contents) with `BigTextStyle`, no visibility flag. Workout foreground notification (`WorkoutSessionService.kt:313-342`) is benign.
- **Impact:** Regulated-mode privacy: medication names (highly sensitive PHI — think psychiatric or HIV meds) and dietary details are readable by anyone who glances at a locked phone. Context: FCM is currently dead in prod so the meal ones don't fire today, but the med reminders are locally scheduled and DO fire.
- **Effort:** 0.5 days · **Autonomy:** agent-solo · **Null-option cost:** continuous PHI exposure on every reminder; a single incident (partner/coworker sees med name) is unrecoverable trust damage.
- **Prompt:** "Add lock-screen privacy to all Android notifications: in `ReminderNotifier.kt` (~line 61-99) and all four builders in `HfMessagingService.kt`, call `.setVisibility(NotificationCompat.VISIBILITY_PRIVATE)` and provide a redacted `publicVersion` (e.g. 'Medication reminder' / 'Meal update ready') via `.setPublicVersion(...)`. Keep channel importance unchanged. Verify no other `NotificationCompat.Builder` sites exist (grep)."

### UX-003 — Web nutrition day renders fetch failure as a legitimate zero-calorie day
- **Severity:** high · **Confidence:** [Certain]
- **Evidence:** `web/app/me/nutrition/page.tsx:126-133` — `getDay(date).catch(() => null)` then `const day = dayResult ? buildDay(...) : emptyDay(date, target);`. The route's error boundary (`web/app/me/error.tsx`) is never reached for this failure; the page shows zero-filled meals identical to a day with no logs.
- **Impact:** Data-integrity display failure in a health app: during a backend blip the user sees "you logged nothing today" and may re-log meals (duplicates) or distrust the product. The in-code comment justifies the catch for *recents* ("a failure just leaves the list empty") but the same pattern was applied to the day itself.
- **Effort:** 0.5 days · **Autonomy:** agent-solo · **Null-option cost:** every transient backend error manufactures false health data on screen; duplicate logging risk.
- **Prompt:** "In `web/app/me/nutrition/page.tsx` (~line 126), `getDay(date).catch(() => null)` conflates fetch failure with an empty day. Distinguish the two: let `getDay` failure throw to the segment `error.tsx` (or render an inline non-blocking 'Couldn't load this day — retry' state), while keeping the `.catch(() => [])` on `getRecentMeals`. Do not render `emptyDay()` on error."

### UX-004 — Async review flows (Adjust-with-AI, Remove Leftovers) have no completion signal without FCM; no timeout state
- **Severity:** medium · **Confidence:** [Certain]
- **Evidence:** Fallback polling exists but is narrow: `android/feature-nutrition/.../NutritionTodayViewModel.kt:559-589` `pollWhileImagesGenerate` — foreground-only, `SETTLE_POLL_BUDGET_MILLIS = 4 * 60 * 1000L` (`:45-54`), stops after 8 failures; re-arms only on screen resume/refresh. Adjust submit UX is an inert row: `AdjustWithAi.kt:54-119` — "Adjusting… you'll get a notification when it's ready." (a promise that is currently false: FCM dead in prod, per shared audit context). `LeftoverUi.kt:39-54` — inert "Analyzing…" pill, no timeout, no cancel. Photo capture likewise has no cancel affordance (`NutritionCapturePanes.kt:385-406`, `AnalyzingPane` with rotating messages).
- **Impact:** With push broken, the *only* way a user learns their adjustment/leftover analysis finished is to reopen the day screen (which re-fetches). The UI literally tells them to wait for a notification that will never arrive. Even with FCM healthy, there is no failure/timeout branch — a lost backend job leaves "Adjusting…" forever on that row.
- **Effort:** 1.5 days · **Autonomy:** agent-solo (UI side) · **Null-option cost:** while FCM is down, every async nutrition flow appears hung; support-yourself debugging cost for the founder.
- **Prompt:** "In feature-nutrition, extend the settle-poll (`NutritionTodayViewModel.pollWhileImagesGenerate`, ~:559) to also poll while any entry `isAdjusting`/`isAnalyzingLeftovers`, and add a stale-pending timeout state (e.g. after N minutes show 'Taking longer than usual · tap to refresh' on the row instead of eternal 'Adjusting…'). Soften the copy in `AdjustWithAi.kt` (~:54-119) that promises a notification, since delivery isn't guaranteed. Do not touch FCM itself (separate fix)."

### UX-005 — Phone dashboard has no error branch and no staleness indicator
- **Severity:** medium · **Confidence:** [Certain]
- **Evidence:** `android/app/.../dashboard/PhoneTodayScreen.kt` renders `CardState.Loading` placeholders (`:177-182`) and loaded data, but no visible branch for `CardState.Error`; failures fall back to cached Room data silently (`DashboardViewModel.kt:187-191` `cachedRecent()` → `loadRecent()`). The only offline UI in the entire app is goals chat's `OfflineNotice` (`GoalsChatScreen.kt:132-137`).
- **Impact:** Offline-first correctly hides *offline*, but it also hides *broken*: a persistent sync failure shows day-old vitals/nutrition with no cue. For weight/meds data that informs decisions, silent staleness is a real risk. The header shows "last updated" (`PhoneHeader`), which partially mitigates — verify it reflects per-card freshness, not app-open time.
- **Effort:** 1 day · **Autonomy:** agent-solo · **Null-option cost:** low day-to-day; high during any prod incident (user sees stale data with no signal — same failure family as the FCM outage going unnoticed).
- **Prompt:** "In `PhoneTodayScreen.kt`/`DashboardViewModel.kt`, `CardState.Error` is modeled but never rendered. Add a lightweight degraded-state treatment: when a card's refresh fails but cache exists, show cached data with a subtle 'couldn't refresh' affordance + retry (the `onRetryWeight` plumbing already exists at `:177-182`); when no cache, render the existing `ErrorState` primitive from core-ui `StateViews.kt`."

### UX-006 — Web sign-out and integration disconnects skip the repo's own confirm convention
- **Severity:** medium · **Confidence:** [Certain]
- **Evidence:** `web/CLAUDE.md` mandates: "Destructive actions (delete, disconnect, anything irreversible) should use `tone: 'danger'` on the confirm." But: disconnect Google Health `web/app/me/profile/page.tsx:250-257` and disconnect Withings `:316-323` are direct form submissions, no `useConfirm`; sign-out `web/app/me/page.tsx:15-17` likewise. All other destructive web actions comply (meal entry `MealSection.tsx:124-138`, drink `DrinkRow.tsx:53-67`, medication `MedicationDetailModal.tsx:244-266`, program `ProgramDetailActions.tsx:103-119`, goal `GoalDetailActions.tsx:97-115`, blood report `BloodReportActions.tsx:17-30` — all `useConfirm`, `tone: "danger"`).
- **Impact:** Disconnecting Withings/Google Health kills forward health-data sync with one click; reconnecting requires a full OAuth round-trip (and for Google Health, the known 7-day-testing-expiry pain). Sign-out is lower stakes.
- **Effort:** 0.5 days · **Autonomy:** agent-solo · **Null-option cost:** occasional accidental disconnects → silent data gaps in weight/sleep history.
- **Prompt:** "In `web/app/me/profile/page.tsx` (~:250 and ~:316), the Google Health and Withings disconnect forms submit directly. Wrap both in the `useConfirm` pattern from `web/CLAUDE.md` (`tone: 'danger'`, copy explaining sync will stop and reconnection requires re-auth), following `BloodReportActions.tsx` as the reference client-component pattern with the server action passed as prop."

### UX-007 — No field-level validation feedback on either platform
- **Severity:** medium · **Confidence:** [Certain]
- **Evidence:** Android: `feature-blood/.../AddReadingScreen.kt:114` renders errors as a global alert-colored `Text`, no `isError`/`supportingText` on any field; `feature-medical/.../AddMedicationScreen.kt:250-252` same pattern (custom `HfTextField` BasicTextField wrapper has no error affordance); validity only gates the submit button (`:259-260` `dose.toDoubleOrNull() != null && unit.isNotBlank()`). Web: `AddReadingButton.tsx` shows submit errors as unassociated text (no `aria-describedby`); `TargetForm.tsx:177-188` uses a form-level warning banner. Positives: numeric keyboards are broadly adopted — 32 `KeyboardType` uses on Android (e.g. `AddReadingScreen.kt:74` `KeyboardType.Decimal`, `AddFoodSheet.kt:554` `KeyboardType.Number`), 43 `type="number"` on web; units are labeled (web `TargetForm.tsx:160-161` "(kcal)/(g)", android blood unit field `AddReadingScreen.kt:81-85`).
- **Impact:** Users learn *that* the form is invalid (disabled button / global message) but not *which field* — worst in the multi-section medication form. Web errors are invisible to screen readers at field level.
- **Effort:** 1.5 days · **Autonomy:** agent-solo · **Null-option cost:** friction and abandoned entries on the longest forms; a11y gap.
- **Prompt:** "Add per-field error affordances: extend `HfTextField` (core-ui) with `isError`/`supportingText` slots styled with `Hf.colors.alert`, and adopt in `AddMedicationScreen.kt` and `AddReadingScreen.kt` (dose must be numeric, unit required, value must parse). On web, associate errors to inputs via `aria-describedby` + `aria-invalid` in `AddReadingButton.tsx` and `TargetForm.tsx`."

### UX-008 — No dark mode on any platform
- **Severity:** medium · **Confidence:** [Certain]
- **Evidence:** Android: zero matches for `isSystemInDarkTheme|darkColorScheme|dynamicColor` across the tree; `core-ui/.../theme/Colors.kt:11-30` defines a single light `HfColors` palette (`canvas = Color(0xFFF0EBE0)`); `HealthFitnessTheme.kt:29` wraps a single `MaterialTheme(`. Web: `web/app/globals.css:48` `color-scheme: light;`, zero `dark:` classes in app/components.
- **Impact:** Med reminders and drink sessions are night-time use cases; a full-brightness cream screen at 11pm is hostile. The token system (single `HfColors` object, `@theme` block) makes this the *cheapest possible time* to add it — drift is near zero (11 raw hex android, 3 web).
- **Effort:** 2-3 days · **Autonomy:** agent-solo with founder palette review · **Null-option cost:** low functionally; each new screen added before dark mode slightly raises the eventual cost, though the token discipline caps it.
- **Prompt:** "Add dark theme: define a dark `HfColors` instance in `core-ui/.../theme/Colors.kt`, switch on `isSystemInDarkTheme()` in `HealthFitnessTheme.kt`, and audit the 11 raw `Color(0x…)` literals outside core-ui (top: `mobile/dashboard/TodayCard.kt` ×2, `Components.kt`, `feature-medical/.../AdherenceSparkline.kt`). Web: add a `.dark`/`prefers-color-scheme` variant of the `@theme` tokens in `globals.css` and remove `color-scheme: light`. Charts (hand-rolled SVG) need their stroke/fill tokens checked."

### UX-009 — i18n effectively not started (0% in 2 of 3 sampled modules); RTL is incidentally clean
- **Severity:** low · **Confidence:** [Certain]
- **Evidence:** feature-nutrition: 0 `stringResource` vs 147 `Text(` calls, no strings.xml; feature-medical: 0 vs 78, no strings.xml; feature-workouts: 101 `stringResource` uses, `feature-workouts/src/main/res/values/strings.xml` with 86 entries. Web: no i18n dependency in `web/package.json`. RTL: zero `Alignment.Left/Right`, `TextAlign.Left/Right`, `Arrangement.Absolute` matches; padding uses `start`-semantics (e.g. `EquipmentRow.kt:88`).
- **Impact:** Honest assessment: for a solo, English-only product this is fine *now*. Retrofit cost grows roughly linearly with string count (~225+ hardcoded UI strings in just two modules and rising). RTL layout is already safe by habit, so localization later is mostly string extraction, not layout surgery.
- **Effort:** 0 now / ~4-6 days at retrofit time · **Autonomy:** agent-solo (mechanical) · **Null-option cost:** deferred, not compounding badly; acceptable to defer indefinitely unless a non-English market appears. Only cheap hygiene: new modules should follow feature-workouts' strings.xml pattern.
- **Prompt:** "(Deferred) If localizing: extract hardcoded `Text("…")` literals in feature-nutrition and feature-medical to per-module `strings.xml` following feature-workouts' existing pattern (86 entries); add next-intl on web. Mechanical, agent-friendly, low risk."

### UX-011 — No first-run experience; web dashboard shows error-toned copy to legitimately-empty new users
- **Severity:** low · **Confidence:** [Likely] (error-vs-empty conflation on cards is Certain in code; the exact new-user API responses aren't verifiable from code alone)
- **Evidence:** Zero matches for "onboarding"/"welcome" flows on Android; new user lands on the dashboard where empty states carry the guidance (good copy exists, e.g. `BloodOverviewScreen.kt:125` "No lab reports yet. Upload a lab PDF to get started.", core-ui `StateViews.kt:116` "Nothing here yet"). Web dashboard cards conflate null with failure: `web/components/dashboard/NutritionCard.tsx:59-62` — `summary === null ? "Couldn't load today's nutrition."`; `WorkoutCard.tsx:38-41` "Couldn't load your workouts." (though `:68` has a proper "No active program" branch once data loads).
- **Impact:** Single-user product today, so onboarding is genuinely optional. The card-copy conflation is the actionable bit: a brand-new (or any) user whose summary endpoint returns null sees failure language, which reads as "app is broken" not "get started."
- **Effort:** 0.5 days (card copy) · **Autonomy:** agent-solo · **Null-option cost:** near zero at n=1 users; becomes the first impression for any future beta user.
- **Prompt:** "In `web/components/dashboard/NutritionCard.tsx` (~:59) and `WorkoutCard.tsx` (~:38), distinguish `null` = no-data from fetch failure (pass an explicit error flag from the server page). No-data should render invitational copy ('Log your first meal') mirroring android's `StateViews.kt` empty-state tone, not 'Couldn't load…'."

### UX-012 — No route-level loading UI on web despite force-dynamic server fetches
- **Severity:** low · **Confidence:** [Certain]
- **Evidence:** `find web/app -name 'loading.tsx'` → zero files; `web/app/me/page.tsx` is `force-dynamic` and fetches before render, as does the nutrition page (multi-await `Promise.all` at `nutrition/page.tsx:125-129`).
- **Impact:** Client-side navigations between /me sections block on server fetch with no skeleton — the app feels frozen on slow links. web/CLAUDE.md itself says "Streaming + Suspense are first-class."
- **Effort:** 0.5-1 day · **Autonomy:** agent-solo · **Null-option cost:** perceived slowness scales with backend latency; invisible on fast local links (why it hasn't hurt yet).
- **Prompt:** "Add `loading.tsx` skeletons to the heavy /me segments (dashboard, nutrition, workouts, blood) matching card layouts, or wrap slow sections in `<Suspense>` with streaming, per web/CLAUDE.md's stated streaming-first policy."

### UX-013 — AddMedication form state lost on process death
- **Severity:** low · **Confidence:** [Certain] (code) / [Likely] (real-world frequency)
- **Evidence:** `android/feature-medical/.../add/AddMedicationViewModel.kt:48-57` — constructor takes no `SavedStateHandle`; all form state in `MutableStateFlow`. Contrast: `NutritionCaptureViewModel.kt:78` persists its label draft via Moshi to SavedStateHandle; `WorkoutSessionViewModel` persists the draft to Room per ADR-0012. Repo-wide `SavedStateHandle`: 43 uses, almost all nav-arg extraction.
- **Impact:** The medication form is the app's longest (name, dose, unit, schedule slots, reminder times); backgrounding to check a pill bottle then returning after process death loses everything. Frequency is low but the moment is precisely when users *do* switch apps.
- **Effort:** 0.5 days · **Autonomy:** agent-solo · **Null-option cost:** rare but rage-inducing loss; pattern already exists in-repo to copy.
- **Prompt:** "Persist AddMedication form state across process death: inject `SavedStateHandle` into `AddMedicationViewModel` and mirror the draft (name/dose/unit/slots/reminders) into it on change, restoring on init — follow the Moshi-draft pattern in `NutritionCaptureViewModel.kt:78`."

### UX-014 — Web sizing drift: ~1,600 arbitrary px values vs a clean color-token story
- **Severity:** low · **Confidence:** [Certain] (count) / [Likely] (that it matters)
- **Evidence:** 1,597 occurrences of `[Npx]` arbitrary Tailwind values in web/app + web/components (grep `\[[0-9]+px\]`), e.g. `text-[13px]`, `text-[28px]` in `NutritionCard.tsx:60,66`; vs only 3 arbitrary hex colors (all `text-[#7C3F0F]`, `GoalCard.tsx:37,67`, `SidebarNavItem.tsx:45` — should be a `@theme` token since it repeats).
- **Impact:** Color tokens are disciplined; type/spacing scale is not — a future type-scale change (or dark-mode contrast pass, UX-008) means touching hundreds of call sites. Low urgency; mostly a "define text-xs/sm/… semantic classes in @theme" cleanup.
- **Effort:** 1-2 days mechanical · **Autonomy:** agent-solo · **Null-option cost:** slow accretion; each new component copies the arbitrary-value habit.
- **Prompt:** "Promote the repeated web font sizes (`text-[9px]`/`[11px]`/`[12px]`/`[13px]`/`[28px]` etc.) into named utilities in `web/app/globals.css` `@theme`, tokenize the thrice-repeated `#7C3F0F` warn-text color, and sweep components. Purely mechanical; verify no visual diff intent."

## HYPOTHESES (unverified — need runtime or deeper tracing)

- **H1 — Back press mid-workout is probably safe but unconfirmed.** `WorkoutSessionScreen.kt` has no `BackHandler` (verified: zero matches), so system back exits without the "Discard workout?" dialog (`:363-371`). However the draft is Room-persisted (ADR-0012 note in `WorkoutSessionViewModel.kt:45-46`) and a foreground service runs, so the session is *likely* resumable, not destroyed. If resume doesn't work cleanly, this escalates to a High destructive-flow finding. Needs runtime verification.
- **H2 — Dashboard "last updated" header may mask per-card staleness** (`PhoneHeader` in PhoneTodayScreen) — if it shows app-refresh time rather than per-source sync time, it worsens UX-005.
- **H3 — Web dashboard `summary === null` for new users**: whether a genuinely-empty account produces null (error copy shown) or a zeroed summary depends on backend response shape, not verifiable from web code alone (UX-011 tagged Likely for this reason).
- **H4 — Wear:** the wear module is a signed-in stub (`MainActivity.kt:37-43`); assumed intentionally pre-MVP, so its absent states were not raised as findings.
